# Red team, round 2 (free-threaded draft)

> Resolutions are in the final runtime-architecture.md, section 'Red team review (second round)'.

## Lens: lifetimes

I found no actual flaw in the core reclaimer protocol in §2.4: stamp before decrement, monotone stamps, min computed before the scan, and the queued Dekker handshake all hold up against the resurrection and ABA interleavings I tried. Every lifetime problem I found is at the edges of the protocol, not inside it:

1. **Destructors break §2.7.** §6's destructor-side ID release cannot be ported as written. It takes a Monitor and dereferences a borrow, so checked builds terminate on the first killed mob that has a respawn timer.
2. **Cycles through captured variables.** Java's GC was silently collecting cycles made of lambda/anonymous-class captures, which the type-level cycle report cannot see. The IdianStone observer leaks a whole Player on every logout with a polished weapon, and item-use observers leak when their removal task is cancelled on delete.
3. **Breakers are too fragile.** They sit at the end of leaveWorld with no finally, so any DAO exception skips them. PlayerStorage.actor is used both as a pointer to its own owner and as a retaining pointer to a foreign Player, which no single generated member type can express.
4. **Stalls and quiescentPoint.** Global epoch pinning is triggered by tasks that borrow nothing (geo collision build, NN training, DB hangs, the cron restart). quiescentPoint is unsafe under nested scopes and ForkJoin joins, and `T&` borrows carry no stamp to catch it.
5. **ID quarantine.** 300 s followed by lowest-free-first reuse is too short for handler-held ID lists such as SummonerAI's, and would delete unrelated Npcs.

Smaller gaps: the KnownList handshake covers one of three pair-add sites; LeakCensus and the watchdog need weak observation, which RefCounted lacks; and Account's replaceable part maps are unspecified.

Every fix stays inside the free-threaded design: a Cleaner queue, capture-aware fieldmap edges plus a PlayerController::onDelete breaker, SelfOrRef with scope-guarded breakers and a zombie breaker, lazy epoch publication, a restricted quiescentPoint with per-element ForkJoin scopes, cursor-based ID reuse, a single addPair, the census on the Reclaimer thread, and PartMap. Add the matching P5/P7 census scenarios (polished-weapon logout, logout during item use, long SummonerAI fight, DB exception during logout) before S0b freezes the kernel API.

### lifetimes-1 [serious]

**Scenario:** A mob in the open world dies and has a respawn timer. NpcController.java:143 schedules the respawn, so pendingRespawns[id] holds a RespawnTask. After decay, the Npc is deleted and its last Ref is dropped. On the Reclaimer thread, §6 has ~AionObject run `if (!RespawnService::setAutoReleaseId(id)) IDFactory::releaseId(id)`. RespawnService.java:95-100 reads the task out of a ConcurrentHashMap (a borrow), and RespawnTask.setReleaseIdOnCompletion (RespawnService.java:201-209) enters synchronized(this), i.e. a Monitor, then dereferences it again through pendingRespawns.get. unregister() (:221-226) needs that same monitor, otherwise the release-on-unregister handoff loses the ID or releases it twice.

**What breaks:** §2.7, L9 and C8 forbid exactly this: taking a Monitor or dereferencing anything inside a destructor. C2 also forbids borrowing outside a TaskScope, and the Reclaimer thread has none. In a checked build (Debug/RelWithDebInfo) the server terminates with a named message on the first killed mob that has a respawn timer, which in practice is nearly every mob. If the monitor is dropped to make it legal, the Dekker handoff with RespawnTask.unregister races, and IDs either leak (the BitSet grows forever) or get released twice ('Couldn't release ID', IDFactory.java:97-98) while the respawned Npc still owns the ID.

**Fix:** Treat this like Java's Cleaner thread. ~AionObject pushes only the int ID onto a lock-free MPSC `CleanerQueue`, which is legal and release-only. The Reclaimer then posts a drain task to the instant pool once per scan when the queue is non-empty. That task runs in a normal TaskScope and executes the Java Cleaner body verbatim (setAutoReleaseId with its SYNCHRONIZED, then IDFactory::releaseId into the quarantine). Update the §6 table and add a P5 test: kill, decay, respawn, and check the IDFactory used-count.

### lifetimes-2 [serious]

**Scenario:** Case 1: a player logs out with a polished (Idian) main-hand weapon. At load, ItemEquipmentListener.java:53 calls IdianStone.onEquip (IdianStone.java:39-60). That creates an anonymous ActionObserver capturing `final Player player` and adds it to player.getObserveController(). leaveWorld (PlayerLeaveWorldService.java:63-153) never unequips and never clears observers. ObserveController.clear() is only called from NpcController.java:132. Case 2: a player logs out in the middle of identify, socket, enchant, polish or tune. ItemActionService.java:26-42 attaches a one-time ItemUseObserver capturing `player`/`item`, and the only removal is inside the ITEM_USE task. leaveWorld → controller.delete() → CreatureController.onDelete → cancelAllTasks (CreatureController.java:415-427) cancels that task, so the observer stays. The same pattern appears in ~15 item actions (ChargeAction:92-94, PolishAction:62-64, TuningAction:79-81, StigmaService:387-392, ...).

**What breaks:** A cycle forms: Player → ObserveController (part) → observer → captured Ref<Player>. Java's GC collects it once the player is unreachable. In C++ the whole Player is leaked for good: storages, items, quest and skill lists, `const Ref<Account>`, PlayerAccountData and account warehouse. Case 1 is deterministic on every logout of such a character, so memory grows without bound over uptime. §5.3's type-level cycles_report cannot see these edges, because they are synthetic captured variables of lambdas and anonymous classes, not declared fields. L16 therefore passes, and the P7 census scenarios only catch it if the test character happens to have a polished weapon.

**Fix:** (1) fieldmap.py must model captures. For every lambda or anonymous class whose instance is stored (passed to addObserver/attach/putRequest/addAttackCalcObserver/schedule, or assigned to a field), add retaining edges from the storing container's class to each captured variable's type, and include them in cycles_report.md. (2) Add a C++ breaker (DEVIATIONS) in PlayerController::onDelete after the Java body: detach all ActionObservers and AttackCalcObservers without firing onRemoved side effects. The ResponseRequester is already handled by denyAll. (3) Add LeakCensus scenarios: logout with a polished weapon equipped, and logout during a 5 s item use.

### lifetimes-3 [serious]

**Scenario:** Case A: the account warehouse is a PlayerStorage whose non-final `actor` field (PlayerStorage.java:15,23) is set to the entering Player at PlayerService.java:133 and cleared only at PlayerLeaveWorldService.java:146. The same PlayerStorage class is a Player part for inventory and warehouse (actor == owner) and an Account part for the account warehouse (actor == a foreign Player). Case B: leaveWorld has no try/finally. A SQLException from PlayerEffectsDAO.storePlayerEffects (:104), PlayerService.storePlayer (:142), or any service call between :80 and :143 skips :144-152. The same happens to the design's own C++ breakers placed 'at the end of leaveWorld' (setTarget(nullptr) for RT-4, setKisk(nullptr) for RT-5). An enter-world that throws after PlayerService.getPlayer also leaves actor set.

**What breaks:** The generator emits one C++ type per Java field, and neither choice works. As OwnerRef (non-retaining, the §3.2 'field typed as the part's owner' rule), the account warehouse's actor dangles once a previous Player is freed, which is a use-after-free through increaseKinah(amount, actor) and onLoadHandler(actor). As Field<Ref<Player>>, every inventory and warehouse part holds a self-cycle to its owner (L16 rejects it). If the Account warehouse edge is retaining, a DB hiccup during logout leaves Account → warehouse → actor → Player → const Ref<Account> uncollectable after the connection closes. A stray target or kisk left by a skipped breaker leaks the same way. Java collects all of these.

**Fix:** (a) Generate `SelfOrRef<T>` for any field whose type equals the owner type of a class that is ever a part. On store it compares with partOwner(): when equal it stores a tagged non-retaining pointer, otherwise it retains. This generalises RT-4's TargetField. (b) Move every C++-only breaker and the Java storage-actor resets into a scope guard that runs even when leaveWorld throws (SCOPE_EXIT in leaveWorld, plus PlayerController::onDelete), and list that in DEVIATIONS. (c) Add a zombie breaker to LeakCensus: for objects removed from World more than N minutes ago, call a virtual breakKnownEdges() that clears target, kisk, storage actors, observers and summon links, and log what it cut.

### lifetimes-4 [serious]

**Scenario:** Several tasks sit in a TaskScope for seconds to minutes. GeoWorldLoader.java:46-47 builds collision data for every mesh on the LongRunning pool while the server is already accepting players. PlayerModelController.java:37 runs model.train(dataSets, 1000) for custom instances. AbstractCronTask.java:44 runs the missed cron job at startup (DB-heavy ranking and cleanup tasks). ShutdownHook.java:38 runs System.exit on the Cron thread via CurrentThreadRunnableRunner, which in Java blocks that thread through the whole shutdown countdown (see comment :91). Every packet task does inline DAO calls, and the commons socketTimeout is optional: Connection.cpp:218 sets read/write timeouts only if > 0, so a hung MySQL (table lock, network loss) blocks a PacketProcessor thread indefinitely inside its scope.

**What breaks:** §2.4's m = min(active epochs) is pinned by one thread that holds no borrows at all, as in geo math or NN training. Nothing server-wide is reclaimed during that time: CopyOnWriteArrayList arrays (ObserveController.java:26, rewritten on every attack-calc observer change), Future shells from every skill and AI timer, KnownObjects from region crossings, and Field<string> boxes. Within the design, §2.6's only remedy is quiescentPoint(), which does not fit inside a neural-net library loop or a blocked socket read. A multi-minute DB stall or a 300 s shutdown countdown turns into unbounded memory growth, plus a 64 MB delayed-free FIFO in checked builds.

**Fix:** Use lazy epoch publication. TaskScope entry records only the scope id. The first borrow-producing operation (Field<Ref>::get, shim get/snapshot, Field<string>::get, Ref(Ptr)) runs the do/while publish before loading. The proof is unchanged, because every pointer load follows publication, and objects reached only through captured or const Refs are retained anyway. Pure-compute and DAO-only tasks then never pin. In addition: a `BlockingRegion` RAII in Future::get, Semaphore::acquire and DB getConnection/execute that feeds the watchdog; a backlog high-water mark (e.g. 1M objects or 256 MB) that dumps the pinning scope's TaskInfo; a mandatory non-zero `database.socket_timeout` for the game server; and the cron restart job posting to the shutdown hook asynchronously (Java initShutdown already uses a virtual thread, ShutdownHook.java:91) instead of blocking in scope.

### lifetimes-5 [serious]

**Scenario:** §2.6 places quiescentPoint() in 'spawnAll per map'. SpawnEngine.java:120-123 runs the per-map body through WORLD_MAPS_DATA.forEachParalllel, and under §7.6 those helpers join the submitter's scope id. spawnInstance, the per-map unit, is also reached from inside ordinary tasks: InstanceService.java:47-48 via getNextAvailableInstance(worldId, player) (:68-71), which uses `player` again at :71 after spawning, called from packet handlers holding Player&/Npc& borrows.

**What breaks:** Called from a ForkJoin helper, quiescentPoint either ends the shared scope, so the other helpers' Ptrs throw in checked builds and are use-after-free in release, or does nothing because the blocked submitter's epoch stays published. Called under a nested scope, it ends the outermost borrow epoch while caller frames still hold `T&` and `Ptr` borrows. §1.2 says nested scopes are a depth counter and quiescentPoint ends 'the current borrow scope'. C1 stamps cover only Ptr, not `T&`, so release builds silently free a Player or instance that a concurrent logout or destroyInstance dropped, and the handler then touches freed memory.

**Fix:** Restrict quiescentPoint structurally. It only takes effect when depth == 1, on a thread that is not joined, inside a scope opened with `TaskScope(info, QuiescentAllowed)` by the loop owner (PeriodicSave, shutdown, the spawnAll top loop). Otherwise it is a no-op with a checked-build warning naming the source_location. Give parallelForEach an `Isolation::PerElementScope` mode for Ref or immortal element ranges (spawnAll), so each helper opens and closes its own scope per element instead of joining. Extend L5b so a function calling quiescentPoint may hold no `T&`/Ptr parameters or locals live across the call, only Refs.

### lifetimes-6 [serious]

**Scenario:** SummonerAI.java:73-90 keeps helper Npcs as bare Integer object IDs in `spawnedNpc` for the whole fight. A raid boss spawns helpers at 75%, players kill them within 2 minutes, and they decay after 2 s (RespawnService.java:34) or 5 min with drops. Their IDs go into the §6 300 s quarantine and are then reused lowest-free-first (IDFactory.java:82-92, 178-185: release() lowers nextMinId). At minute 20 the boss resets: handleBackHome (:48-51) → removeAndResetHelperSpawns calls World.findVisibleObject(id) and deletes whatever now owns each ID if it is spawned (:76-78). Similarly, Npc.getCreator() (Npc.java:318-320) resolves an int creatorId for Npcs that can outlive an auto-release creator.

**What breaks:** The unrelated Npc that received the reused ID is deleted: a respawned field mob, a siege or base guard, a quest Npc. The 300 s figure assumed DecayTask is the longest bare-int holder, but handler-held ID lists last for encounter lifetimes, which are unbounded. In Java these helpers were usually promoted to old gen and released only by a later mixed or full GC. EBR's ~20 ms release plus lowest-first reuse makes the collision routine on any fight longer than about 5 minutes.

**Fix:** Change IDFactory reuse order rather than lengthening a timer. Keep a monotone cursor for auto-release IDs (allocate upward, wrap to the lowest free ID only when the top of the configured range is reached), so the reuse interval is roughly free-space divided by allocation rate (days). Keep the 300 s FIFO as a floor. Checked builds log in World.storeObject when an ID released less than 1 h ago is reassigned, naming the previous class. Add an entry to DEVIATIONS (IDs are opaque to the client).

### lifetimes-7 [minor]

**Scenario:** The §5.3 spawn handshake is shown only for the region loop, KnownList.java:192-193. Two other pair-add sites exist: KnownList.java:175-178, where a player adds instance-wide flag Npcs, and FlagKnownList.java:18-21, where the flag's update() adds every player in the instance through worldMapInstance.forEachPlayer. FlagKnownList.java:17 also removes only the flag's side (knownObjects.values().removeIf) and never the player's reverse entry. Race: a flag's update() on one thread snapshots the instance players while a player logs out on another (World.java:318-325: setIsSpawned(false), region remove, clearKnownlist). The add pair lands after the clear.

**What breaks:** The zombie Player stays in the flag's KnownList and the flag stays in the player's list, forming a retaining two-way cycle. The flag's removeIf never fires, because the zombie's WorldPosition still names the same instance. Flags are long-lived (sieges, instances), so the entire logged-out Player plus Account is kept until the flag despawns. The design claims this race class is closed.

**Fix:** Implement one `KnownList::addPair(VisibleObject& a, VisibleObject& b)` containing the add/add/post-check/del handshake, route all three sites through it, and have the lint reject direct `add(` calls outside it. Port FlagKnownList's removeIf as a two-sided del (C++ deviation), or apply the same isSpawned post-check to it.

### lifetimes-8 [minor]

**Scenario:** §5.4 LeakCensus records every AionObject removed from World and later logs 'class, id, refcount' if it is still alive after 10 minutes. §4.3's watchdog records `{thread, lock, owner}` for waits on Monitors embedded in RefCounted objects and walks them from its own thread every second. RefCounted (§2.2) has no weak count, and neither the census nor the watchdog is described as holding Refs or running in a scope.

**What breaks:** To avoid keeping objects alive, the census has to store raw pointers. Its periodic scan then reads count/vtable/objectId while the Reclaimer deletes the object: a use-after-free on a production thread, since the census is on by default. Likewise, the watchdog dereferences a lock pointer whose owning object was freed after the waiter left its scope. With Refs instead, the census itself becomes the leak it is meant to report.

**Fix:** Run the census scan on the Reclaimer thread between scans, the only place where frees happen, so raw pointers are stable there. ~AionObject erases its census record through a Reclaimer-thread-only structure (no lock, no dereference). The census copies class name and objectId at registration time. The watchdog copies the lock class name and owner thread id into the wait record at wait start and never dereferences the lock pointer afterwards.

### lifetimes-9 [minor]

**Scenario:** RT-1 makes PlayerAccountData and the account warehouse parts of Account, but Java replaces both. Account.java:143-146 does `players.put` over an existing PlayerAccountData. AccountService.java:68,80 and PlayerEnterWorldService.java:119-123 call setAccountWarehouse on the stale-online path (client crash, reconnect, enter world). AccountService.java:53-58 removes PADs through an iterator. §2.3 only offers PartSlot (single slot, retire-to-owner) and §9's PartList (append-only).

**What breaks:** A map shim holding unique_ptr parts destroys the replaced part immediately, bypassing EBR, while the same task may still hold borrows taken before the put (e.g. :91/:98). Retire-to-owner semantics instead accumulate one full warehouse (all items) per stale-online re-entry for the lifetime of the connection's Account. Neither behaviour is specified, so agents will choose differently.

**Fix:** Add `PartMap<K, P>`: replaced or removed parts are retired to the Reclaimer (with an epoch stamp and a deferred destructor that holds a Ref to the owner until freed), not to the owner's list. Declare Account.players and Account.accountWarehouse as PartMap/PartSlot overrides with retire-to-reclaimer in fieldmap.toml, and add a P7 scenario: crash, reconnect, enter world 50 times, then check the Account's retired bytes.

## Lens: concurrency-porting

Most of the free-threaded design holds up against the Java code. EBR, Field and eager serialization are sound for the paths I traced, and the KnownList handshake survives the concurrent add/despawn interleavings I tried.

One fatal problem: the flat CONTAINER rank, together with 'no Monitor under a ranked lock' kept in release builds (C14), makes ordinary Java ConcurrentHashMap.compute callbacks throw:
- CreatureGameStats.java:73-84 takes `synchronized (statFunctions)` inside compute, so every buff and equip throws.
- PlayerContainer.java:51-54 puts into the same map inside compute, so rename throws.
- GaleCycloneAI, LegionService, SpawnsData and Preview have similar callbacks.
Fix: callbacks run under reentrant, lockdep-tracked stripe Monitors, and the ranked leaf lock is kept only for slot operations.

The serious findings are places where the mechanical rules do not match the Java code:
- **Destructor contradiction.** The prescribed `~AionObject` calls RespawnService, which takes a Monitor and dereferences a pointer, both of which the destructor rules forbid.
- **Stored callbacks.** About 150 observer, request, cron and event-end callbacks are outside L5 and invisible to fieldmap and cycles. IdianStone leaks a whole Player graph on every logout.
- **Reclamation stall.** A single //fixpath scope stops reclamation server-wide for minutes, far beyond the 5 s the design assumes.
- **Hub parts missed.** Creature's stats, effects, knownlist and controllers are wired by setter and late setOwner, so the part rule misses them. Result: a Ref cycle in every creature.
- **Transient classes.** Classes like Stat2 and QuestEnv default to RefCounted K4. That invites RefCounted objects on the stack (Reclaimer deletes stack memory) and puts refcount traffic on hot creatures.
- **Identity vs equals.** Shim remove/contains use identity, contradicting Java objectId equals across relogin (DropNpc loot lock, doubled RvR event rewards).

Minor: L11 contradicts the promised Iterator.remove support; lockdep classes by dynamic type produce false ArrayList cycles and leave monitorOf gaps; snapshots on hot read paths have a measurable cost.

All fixes stay within D1: generator and lint extensions, a released-ID drain task, callback concepts, interval-based reclamation, Java-equals shims and stripe Monitors.

### concurrency-porting-1 [fatal]

**Scenario:** Callbacks of ConcurrentHashMap.compute/computeIfAbsent run under the flat CONTAINER stripe lock, and Java code does a lot inside them. (1) CreatureGameStats.java:73-84: `stats.compute(...)` takes `synchronized (statFunctions)` inside the callback. This runs on every addEffectOnly: every buff, passive, equip, set bonus and enchant. (2) PlayerContainer.java:51-54: `playersByName.compute(oldName, ...)` calls `playersByName.put(newName, player)` on the same map from inside the callback. (3) GaleCycloneAI.java:31-35: computeIfAbsent calls `player.getObserveController().addObserver`, which is `synchronized (observers)` (ObserveController.java:37). (4) LegionService.java:154-159: computeIfAbsent runs `LegionMemberDAO.loadLegionMember` plus `PlayerService.getOrLoadPlayerCommonData`, which does more map operations. (5) SpawnsData.java:83-96: `mapSpawns.computeIfAbsent` nested inside `allSpawnMaps.compute`. (6) Preview.java:211-226: schedule, cancel(true) and sendPacket (eager serialization, so writeImpl runs) inside compute.

**What breaks:** §4.1 says acquiring a Monitor while any rank > 0 is held throws, and acquiring rank r needs max held rank < r. §12.5 C14 keeps those rank checks in release builds. Consequences: (1) throws IllegalStateException on every stat-function add, so buffs, equips and passives all break. (2) and (5) take CONTAINER while already holding CONTAINER, which throws; without the check, a same-stripe put (1 in 16) self-deadlocks on a non-reentrant stripe mutex. So a character rename throws. (3) a gale cyclone throws on every player it sees. (4) the rank violation throws, and the DB round trip holds 1/16 of the map's writers. Java allows all of these: CHM locks only the bin with a Java monitor, and a monitor can nest anything. The 'mechanical' port throws in the most common gameplay path, and the design's own §14g example only works because its callback happens to be lock-free.

**Fix:** Split the shim's locking in two. (a) Callbacks of compute/computeIfAbsent/computeIfPresent/merge run under a per-stripe Monitor-level lock: reentrant, rank 0, lockdep class `Owner::field`. put/remove/replace on the same stripe take the same lock, so Java's bin atomicity is kept. (b) A short CONTAINER leaf mutex (or lock-free EBR-protected reads) guards only the slot read/store and is never held across user code. Detect recursion on the same key and throw IllegalStateException("Recursive update") as Java does; different keys on the same stripe are allowed through reentrancy. Keep the 'never calls out' rank rule only for operations without callbacks. Apply the same to `sort(comparator)` and PriorityQueue comparators. Add PCT scenarios for nested compute and compute that takes a Monitor, and a conformance test for the six sites above.

### concurrency-porting-2 [serious]

**Scenario:** §6 prescribes `~AionObject: if (!RespawnService::setAutoReleaseId(id)) IDFactory::releaseId(id)`. RespawnService.java:95-100 does `pendingRespawns.get(objectId)` and then `respawn.setReleaseIdOnCompletion()`, which is `synchronized (this)` and reads `pendingRespawns` again (RespawnService.java:200-208). The usual case: a mob dies, its corpse decays (DecayTask, RespawnService.java:57-62) while its respawn is still pending, and the last Ref goes away.

**What breaks:** The Reclaimer thread runs a destructor that (a) does a container get, which C2 says needs a TaskScope, (b) dereferences a Ptr<RespawnTask>, forbidden by §2.7/L9 and terminating under C8, and (c) takes a Monitor, forbidden by L9. Checked builds terminate on almost the first normal mob kill, and P5 cannot pass. In release builds the Reclaimer blocks on a game Monitor, so reclamation for the whole server depends on game lock contention, and lockdep sees a game lock under Reclaimer context. The design contradicts itself.

**Fix:** Keep Java's split between Cleaner and GC. `~AionObject` only pushes `objectId` onto a lock-free `ReleasedIds` MPSC queue. A registered periodic task on the instant pool drains it inside a normal TaskScope and runs the Java Cleaner body (setAutoReleaseId, else releaseId). The quarantine applies after that. L9 stays strict, and a destructor test checks that no destructor calls into services.

### concurrency-porting-3 [serious]

**Scenario:** Callbacks stored anywhere other than ThreadPoolManager. About 96 `new XxxObserver(){...}` anonymous or inner classes (IdianStone.java:39-60 captures `final Player player`; GaleCycloneAI.java:55-88 is an inner class using the outer AI's `observed`; Equipment.java:733 captures `responder`; AIActions.java:102). Also `new DeathObserver(_ -> {...})` lambdas (WorldRaid.java:144), 32 `putRequest`/`addOnEventEndTask` sites and 26 `CronService.schedule` lambdas. None of these is a ThreadPoolManager schedule site.

**What breaks:** (a) L5 and the Pin/UnpinnedTask concepts cover only ThreadPoolManager overloads. An agent porting IdianStone writes `[&player]`, or captures a `Ptr`, into an observer stored in the Player's shared ObserveController list. It later fires from another thread's task and dereferences freed memory, and neither lint nor C1 sees it, because stamps are checked only on dereference in that thread. (b) fieldmap.py derives members from declared fields, so javac's implicit captures (`val$player`, `this$0`) never reach L1/L2 or cycles_report. IdianStone forms a cycle: Player → Equipment → Item → IdianStone.actionListener (Field) → captured Player. The Player's ObserveController is never cleared (the only `getObserveController().clear()` is NpcController.java:132). So every logout with a polished main-hand weapon leaks the whole Player, Account and storage graph, and L16 cannot report it.

**Fix:** Give stored callbacks the task rules. Callback-holding base types (ActionObserver, DeathObserver lambda, RequestResponseHandler, CronService jobs, Event end tasks) accept only `Pin + invocable` or `UnpinnedTask`, the same concepts as ThreadPoolManager. Anonymous classes are ported as named nested structs. fieldmap.py models captured locals and outer `this` as generated `const Ref<X>` members, so L1/L2/L16 apply to them. Add a C++ breaker at the end of leaveWorld: `getObserveController().clear()` plus clearing attackCalcObservers. Add census scenarios for logout with a polished weapon and with a pending dialog observer.

### concurrency-porting-4 [serious]

**Scenario:** FixPath.java:85-133: one `execute` task teleports through every step of a walker route. For each step, getZ (FixPath.java:139-161) blocks in `waitTask[0].get(5, SECONDS)`. §2.6 assumes a 5 s scope, but the scope actually covers the whole loop: 100+ steps at up to 5 s each, so 5-10 minutes. QuestEngine.java:108 `executeLongRunning(QuestSpawnAnalyzer.run...)` is another scope that stays open far longer than the examples in §2.6.

**What breaks:** EBR is global. While one instant-pool thread sits in that scope, nothing retired anywhere on the server is freed. That includes KnownObjects from every region crossing, Effects, Futures, packets' Ref members and despawned Npcs. Memory grows without bound for minutes. The watchdog only warns after 10 s and cannot fix it. A GM running //fixpath on a live server is enough.

**Fix:** Short term: call `quiescentPoint()` at the top of each route-step iteration. The loop holds only `admin` (pinned Ref) and the template (immortal), so it satisfies L5b. Structural: move to interval-based reclamation (2GE-IBR). Each object records its birth epoch; each thread publishes [scopeBegin, lastReadEpoch], with lastReadEpoch refreshed by the Field<Ref>/container read barrier only when the global epoch changed, so it stays cheap. A blocked thread then pins only objects born before its last read, and the stall cannot spread to the rest of the server. Add a lint warning for `Future::get(timeout)`, `Semaphore.acquire` and long DAO loops inside a scope without a preceding quiescentPoint or a `// long-scope:` waiver.

### concurrency-porting-5 [serious]

**Scenario:** The central creature parts do not match the part-detection rule. Creature.java:44-53 has non-final gameStats, lifeStats, effectController, moveController and observeController; VisibleObject.java:31 has knownlist. They are assigned through public setters from subclass constructors (Npc.java:70-71, Player.java:213-214) and from other services on half-built objects (VisibleObjectSpawner.java:60-250, PvpMapHandler.java:167-169). Controllers are built before their owner (`new Npc(new NpcController(), ...)`, 26 `new XController()` sites) and wired later with `controller.setOwner(this)` (VisibleObjectController.java:20-28, Npc.java:58).

**What breaks:** The rule only knows `final X x = new X(this)` or `new X(this)` inside the owner's constructor, so it matches none of these. The effectively-final scan fails too, because the setters assign from other files. The generator emits `Field<Ref<NpcGameStats>>`, and NpcGameStats' `protected final T owner` becomes `const Ref<Npc>`. That is a per-instance cycle for every creature and every controller. L16 fails on the core hub types, and OwnedPart(owner) cannot express 'owner bound after construction'. S0b then has to hand-design the most important headers, which is exactly the judgement the mapping was meant to remove, and the §3.2 override list does not mention these.

**Fix:** Extend fieldmap.py part detection: (a) `setF(new X(this))` in any constructor of the owner or a subclass, or `r.setF(new X(r))` anywhere, makes F a `PartSlot<X>`; (b) `super(..., new XController(), ...)` plus `x.setOwner(this)` in the constructor is the late-bound part pattern. X derives `OwnedPart` with `bindOwner(O&)`, which may be called once before publication (C11 extended) and turns the `owner` field into `Final<O*>`. List these patterns in `parts.json` with the evidence line, and make S0b review the generated result instead of writing overrides.

### concurrency-porting-6 [serious]

**Scenario:** Short-lived objects become K4 by default. Stat2 has `private final Creature owner` (Stat2.java:12) and non-final float rates; a new AdditionStat or ReverseStat is created on every getStat (CreatureGameStats.java:119-127): dozens per attack, around 100 per SM_STATS_INFO. QuestEnv has 87 `new QuestEnv(...)` sites and is used as a temporary, but it is also captured by tasks (_20506MuscleOverMind.java:135 `schedule(() -> restoreQuestStep(env))`) and stored (FollowingNpcCheckTask.java:17).

**What breaks:** (a) Porting hazard. Rule 6 turns `new SM_X(..)` into a stack temporary, and nothing says other `new` expressions differ, so agents will write `QuestEnv env(nullptr, player, 0);` on the stack. A handler that does `Ref<QuestEnv>(env)` into a task goes 0→1→0, the object is retired, and the Reclaimer `delete`s stack memory: heap corruption that C3 cannot catch because cookies look ALIVE. (b) Performance. Every Stat2 or QuestEnv becomes a heap RefCounted with atomic Fields. Its `const Ref<Creature>` makes each stat computation do retain + CAS-max epoch stamp + release on the hot creature's count cache line. Many PacketProcessor, ScheduledPool and ForkJoin threads do this at once on a boss or player, so the claim that hot objects are borrowed does not hold.

**Fix:** (1) Infer K5 CONFINED automatically. fieldmap.py builds the escape graph, and a class that never appears in a K4 member, container element, captured variable or packet member gets plain members with `Ptr`/`T&` references (valid for the task). QuestEnv escapes and stays K4, Stat2 does not. (2) Make stack instantiation of RefCounted a compile error: generated protected destructors and `static Ref<T> create(...)`, and makeRef as the only path that sets the cookie. `retain()` on an object without the makeRef cookie terminates in checked builds. (3) Release fast path: CAS-decrement without stamping while count > 1, and stamp only right before the 1→0 CAS. The safety proof only needs the stamp before the 0 transition, and this takes the epoch write off hot releases.

### concurrency-porting-7 [serious]

**Scenario:** §3.3 says shim `remove`/`contains` use identity for Ref elements. Java AionObject.equals/hashCode compare objectId (AionObject.java:48-64). Code relies on that across relogin instances. DropNpc.java:122-134 `playerStatus.add(player)` / `remove(player)` / `contains(player)` on a Collection<Player>. SiegeService.java:684 `rvrEventPlayers.contains(player)` on a HashSet<Player>. AutoHarmonyInstance.java:75 `players.remove(player)`.

**What breaks:** A player who opens loot, relogs, and closes or reopens it: remove(newInstance) by identity leaves the old instance in playerStatus. The corpse stays marked as being looted, and the stale Player plus Account stays retained. `checkRvrEventPlayer` adds the same character twice after relogin, so the reward is doubled. §5.2 itself says relogin instances compare `equals`, so the shim contradicts the design's own identity rule.

**Fix:** Shims use Java semantics derived from the element's Java class. If the class (or a superclass other than Object) overrides equals/hashCode, `remove`/`contains`/`indexOf`/HashSet/HashMap keys use the generated `equals` and `hashCode` (ObjectIdHash for AionObject). Only classes without an override use identity. fieldmap.json records `hasEquals` per class. `Iterator.remove` and `removeIf` matches stay identity-based, which is correct for positional removal.

### concurrency-porting-8 [minor]

**Scenario:** L11 forbids storing `.begin()` of a shim, but §3.3 promises that `Iterator.remove()` works. Java uses explicit iterators with removal: ObserveController.java:64-71 collects matching observers and calls `iterator.remove()` on one-time ones in the same pass under `synchronized (observers)`, and :184-190 does the same for abortItemUseObservers. The codebase has 49 `.iterator()` sites and 13 `it.remove()`.

**What breaks:** Porting agents get no mechanical mapping and each rewrites these loops differently: removeIf with side-effect captures, index loops, or copy-then-remove. That changes when onRemoved runs, and removeIf's predicate on a snapshot combined with removal by identity differs from positional removal. Four to six agents will produce inconsistent semantics in ObserveController, the busiest callback path.

**Fix:** Add a Java-named `iterator()` on every shim, returning a `JavaIterator<T>` (hasNext/next/remove) that owns its snapshot and removes the last returned element by identity from the live collection. L11 then allows `auto it = x.iterator();` locals and still forbids `begin()` stored in variables. Add ObserveController to the P9 calibration set.

### concurrency-porting-9 [minor]

**Scenario:** Lockdep's lock class is the dynamic type of the synchronized object. SummonerAI.java:74-81 holds `synchronized (spawnedNpc)` (an ArrayList) and calls `npc.getController().delete()`. That path goes through despawn, KnownList.clear (KnownList monitor), NpcController.onDespawn and `synchronized (observers)`, another ArrayList (ObserveController.java:285). Separately, CreatureGameStats takes `synchronized (functions)` and `synchronized (statFunctions)`, also ArrayLists.

**What breaks:** All ArrayList shim Monitors and all AtomicBoolean monitors share one lock class. Edges such as ArrayList→KnownList (SummonerAI) and KnownList→ArrayList (observers under clear/notSee paths) show up as a 'cycle' although the lists are different fields. With `failOnReport` in CTest, handler tests fail or collect suppressions, and real inversions get lost in the noise. There are also coverage gaps: `synchronized (isAggred)` on AtomicBoolean fields (CaptainMuruganAI.java:23 and four other AIs), `synchronized (guard)` in AionConnection.java:205 (a shared_ptr type, not in the monitorOf list), and CHM values used as monitors (statFunctions) require shim collections that are RefCounted.

**Fix:** The generator gives every member Monitor, shim and Atomic* member a static lock-class tag `DeclaringClass::field`. `SYNCHRONIZED(*this)` keeps the dynamic type, and CHM stripe Monitors use `Owner::field#stripe`. Every Atomic* and collection shim implements `monitor()`. AionConnection gets a Monitor member. Collection shims have RefCounted variants so they can be map values (`ConcurrentHashMap<StatEnum, Ref<ArrayList<...>>>`).

### concurrency-porting-10 [minor]

**Scenario:** Hot read paths go through snapshots. Each SM_MOVE broadcast from MoveTaskManager does KnownList.forEachPlayer, a CHM snapshot across 16 stripes plus a vector allocation. Each movement step calls ObserveController.notifyMoveObservers (ObserveController.java:59-74): Monitor + container lock + snapshot iterator. EffectController holds its StampedLock read lock while iterating `abnormalEffectMap.values()`, which adds a second internal lock and an allocation per call (EffectController.java:386-422). Java does these reads lock-free or without allocating.

**What breaks:** Nothing breaks, but the cost is paid per movement tick on cores − 1 ForkJoin threads and per attack: roughly 16 uncontended locks and one allocation per broadcast and per observer notification, on top of the eager serialization now done under the mover's KnownList monitor. At hobby scale this is measurable but not a cliff. It will dominate P4's per-tick profile, and the §15.1 estimate leaves it out.

**Fix:** The Reclaimer already exists, so use it for readers. ConcurrentHashMap/CopyOnWriteArrayList shims can do lock-free get/iteration over EBR-retired tables, iterating in place with weak consistency and no snapshot, which matches Java. Keep snapshots only for plain Java ArrayList/HashMap shims. Add an `isEmpty()` fast path before snapshotting, as Java's ObserveController does. Measure all of this explicitly in P4.

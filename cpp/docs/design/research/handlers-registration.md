# handlers-registration

## Summary
Game-server handlers are 1,729 Java files (158k lines) under D:\aion-server\game-server\data\handlers: quest 1,035 files (95.5k lines), ai 461 (33.3k), instance 78 (17.2k), admincommands 101 (8.8k), consolecommands 35 (1.8k), playercommands 16 (1.2k), zone 3 (135). Five engines load them. QuestEngine, AIEngine, InstanceEngine, ChatProcessor and ZoneService each create a commons ScriptManager that compiles one directory at startup. A ClassListener then walks every compiled public, non-abstract class and registers it by base type plus an annotation. Four discovery keys are used: @AIName(String) with 457 uses, @InstanceID(int) with 73, @ZoneNameAnnotation(value = space-separated zone names, questId) with 2, and no annotation for quests and chat commands (the key comes from the constructed object: getQuestId() or prefix+alias). @OnClassLoad/@OnClassUnload are registered in 4 engines but used by 0 handlers. The registries hold different things. AI, instance and zone registries store Class objects and build a new instance through reflection: one AI per Creature, one handler per WorldMapInstance, one zone handler per zone instance. Quest and command registries hold one stateless singleton each. All 1,035 script quests extend AbstractQuestHandler directly and register events in register() through ~7,000 qe.registerX/addOnX calls. Another 4,184 quests need no handler file: they come from 15 XML element types in static_data/quest_script_data (e.g. item_collecting 1,681, monster_hunt 1,163), polymorphic through JAXB @XmlElements, and are built by 16 core template classes. The script and XML quest IDs do not overlap, so the expected total is 5,219 quest handlers (not verified at runtime). Handlers reach the core almost only through static singletons and static utilities: PacketSendUtility 1,684 refs, ThreadPoolManager 685, QuestService 331, SkillEngine 281, TeleportService 271, DataManager ~90. Across categories they import 484 distinct core classes; quests import only 76, admin commands 249. Handlers barely depend on each other: AI subclasses import handler AI base classes 288 times (~34 base classes), consolecommands look up 3 admin command classes by Class, and no quest, instance or zone handler references another category. Patterns that are hard in C++: reflective construction with owner-type matching and a generic-type check (AIEngine), AI objects created inside the Creature constructor with a partially built `this`, and delayed tasks scheduled from handlers (219 AI files, 44 instance, 36 quest) whose captured objects may be gone when the task runs (117 of those AI files keep no Future). Also: reflective admin commands (Configure, Ai, Debug, Dye), JAXB inside handlers (6 files), class-name lookups, reload commands, and QuestSpawnAnalyzer, which regex-parses the .java handler sources at runtime. Registration cannot run during static initialization: quest constructors read DataManager.QUEST_DATA, command registration reads CommandsConfig.ACCESS_LEVELS, and AI validation needs NPC_DATA. Registries must therefore store factories, and the engines instantiate after static data and config have loaded. My recommendation for ~1,600 C++ handler files is a one-line marker macro per handler plus a CMake-generated registration table (design 2). It works with the existing STATIC-library helper (aion_add_library) and with unity builds, needs no /WHOLEARCHIVE, and detects duplicates while generating.

## Key findings
- **Registration must store factories, not instances. The engines instantiate handlers only after config and static data are loaded, so no handler is constructed during static initialization.**
  - Evidence: AbstractQuestHandler.java:59 reads DataManager.QUEST_DATA in the constructor. ChatProcessor.java:52 calls cmd.getLevel(), which reads CommandsConfig.ACCESS_LEVELS (NPE if the alias is missing). AIEngine.java:102-114 validates against DataManager.NPC_DATA. GameServer.java:97-101 inits the engines after DataManager.getInstance().
  - C++: Registrar or table entries hold `{key, factory}` only. QuestEngine::init/ChatProcessor::init call the factories. Registrars must not log or read config (static init runs before Logging::init; see CONVENTIONS logging note on static init).
- **Discovery uses exactly four keys. Two categories have no annotation, because the key comes from the constructed object.**
  - Evidence: @AIName(String) 457x; @InstanceID(int) 73x; @ZoneNameAnnotation(value, questId) 2x; quests use getQuestId() (1,030 constant `super(<int>)`, 5 `super(_questId)` constants); commands use prefix+alias from the ctor. @OnClassLoad/@OnClassUnload are used 0 times.
  - C++: Macro signatures: AI(name, class), INSTANCE(mapId, class), ZONE("names", questId, class), QUEST(class), COMMAND(class). Quest ids and command aliases can stay in constructors, as in Java. Putting the quest id in the macro would enable compile-time or generation-time duplicate checks; Java only warns on duplicates (QuestEngine.java:892-898).
- **AI construction relies on reflection. It uses constructor lookup by the owner's runtime class and a generic-type walk, and it happens inside the Creature constructor.**
  - Evidence: Creature.java:67 `this.ai = AIEngine.getInstance().newAI(aiName, this)` runs in the base-class constructor. AIEngine.java:64-100 matches the constructor parameter type against owner.getClass(), which in Java is already the most-derived class. AIEngine.java:118-136 findDefaultOwnerType. 459 ctors take Npc, 1 takes Summon (SiegeWeaponAI). AbstractAI.getName() reads the annotation of getClass() (AbstractAI.java:71).
  - C++: Use two-phase construction: create the AI after the concrete Creature object exists, from a factory/post-construct step (in a C++ base constructor the dynamic type is still the base). Factory signature e.g. `std::unique_ptr<AbstractAI>(*)(Creature&)`, generated by a template that static_casts or dynamic_casts to the declared owner type. The owner-type check becomes compile-time (template requires a ctor from OwnerT&). The runtime check is one dynamic_cast, which replaces validateScripts' reflection. Store the registry name in the AI object for getName(). `//ai set` (Ai.java:86-89) needs a real `Creature::setAi()`.
- **AI startup validation is all-or-nothing, so partial porting blocks server start.**
  - Evidence: AIEngine.java:112-114 throws GameServerError if any of the 432 npc_template AI names lacks a handler. 63,123 templates have ai=; aggressive (39,358) and general (11,770) live in data/handlers/ai root, not in core.
  - C++: Add a dev/config switch: missing AI name → warn and fall back to GeneralNpcAI/DummyAI. Port the 43 root AI handlers (2,851 lines) in phase 5 together with the AI framework (src/ai 3,450 lines), since 'fight a mob' needs aggressive/general.
- **Delayed tasks in handlers capture `this` (AI or instance handler), Player, QuestState or Npc without lifetime guarantees. In Java the GC keeps them alive.**
  - Evidence: 219 AI files schedule tasks and 117 of them keep no Future field (fire-and-forget). 44 instance handler files schedule, 17 of them without onInstanceDestroy. 36 quest files schedule (e.g. quest/altgard/_2208MauInTenMinutesADay.java:85-94 anonymous Runnable captures player, qs, env for 3 s). ai/instance/beshmundirTemple/AethicFieldGeneratorAI.java: scheduleAtFixedRate lambda calls isDead()/getKnownList() on the owner. instance/dredgion/DredgionInstance.java:81-115 schedules on `instance` up to 42 min ahead.
  - C++: Input for decision (A). Handler code needs a task API whose callbacks run only if their target is still alive, e.g. `ThreadPoolManager::schedule(weakOrHandle, fn)`, or shared_ptr/weak_ptr capture of AI, Npc, Player and WorldMapInstance, or tasks owned by the AI/instance and auto-cancelled in its destructor. A raw `[this]` capture would be UB in ~400 files. Handlers mostly look objects up by id (getNpc/getNpcs 511x in ai+instance) and store few object references (18 Npc fields, 11 collections), which fits handle/ID lookups.
- **Quest script handlers are extremely uniform and have a narrow API, which makes them the best candidates for mechanical or semi-automatic translation and parallel batches.**
  - Evidence: All 1,035 extend AbstractQuestHandler directly. 76 distinct core imports. 0 mutable object fields and 0 nested classes (only 20 files with effectively constant int[] fields). Median ~85 lines. Structure is ctor `super(id)` + register() of qe.* calls + onDialogEvent switch (1,601 switches) + helper calls (sendQuestDialog 4,116 ...). 30 anonymous Runnables in 27 files.
  - C++: Port AbstractQuestHandler (1,290 lines) and QuestEngine (7,183 lines incl. templates) first, keeping the Java helper names. A text-level Java→C++ converter for quest files (not verified; rough guess ~80% automatic) could replace hand-porting 95k lines. Quest handlers can share one PCH containing AbstractQuestHandler/QuestEnv/QuestState/Player/Npc/DialogAction.
- **4,184 of the 5,219 quest handlers are data-driven and need no handler files. They are polymorphic JAXB elements handled by 16 core template classes.**
  - Evidence: dataholders/XMLQuests.java:20-27 @XmlElements (15 types used). QuestEngine.java:104-105 `xmlQuest.register(this)`. XmlQuestData.java/ReportToData.java `register()` does `questEngine.addQuestHandler(new ReportTo(...))`. The ID sets of scripts and XML are disjoint (checked with comm).
  - C++: No registry needed: the static-data generator (B) must support xsi-free element-name polymorphism (@XmlElements choice → std::variant or unique_ptr<XMLQuest>) and call a virtual/visited `register(QuestEngine&)`. //reload quests rebuilds these tables at runtime, so QuestEngine's 27 event maps need a swap or lock scheme.
- **Handlers depend on each other only through inheritance within a category, plus 3 class-typed command lookups. The core never references handler classes, only AI names as strings.**
  - Evidence: ai imports handler `ai.*` classes 288x (~34 handler classes used as bases); instance has 15 handler base classes; zone has PvPZone; consolecommands→admincommands: Attrbonus.java:26 getCommand(Stat.class), Deletecquest.java:28 getCommand(Quest.class), Teleportto.java:23,29 getCommand(GoTo.class). Core string checks: DropRegistrationService.java:87,114 ("quest_use_item","chest"), CM_HOUSE_TELEPORT.java:63 ("friendportal"), FollowingNpcCheckTask.java:67 ("following"), PlayerTeamDistributionService.java:98 ("chest"), VisibleObjectSpawner.java:246 ("siege_weapon").
  - C++: Only base-class handlers need headers. Every leaf handler can be a single .cpp with no header, which keeps compile units independent and batches parallelizable. `ChatProcessor::getCommand<T>()` via dynamic_cast replaces getCommand(Class). Keep AI name strings and getName() semantics.
- **Several reflective or JVM-specific features in commands and core helpers have no direct C++ equivalent.**
  - Evidence: admincommands/Configure.java:131 (static config fields by name, an open decision in PORTING_PLAN), Ai.java:86-89 (replace final field), Debug.java:79 (private GameServer.nioServer), Dye.java:54 (java.awt.Color by name), Id.java (getClass().getSimpleName() shown to players), ChatCommand.java:167-175 (parses Java 'No enum constant a.b.C.x' exception messages and Class.forName to list enum values), Effects.java:182 (EffectType from class simple name), QuestSpawnAnalyzer.java:95-120 (regex-scans data/handlers/**/*.java at runtime; enabled by gameserver.analysis.quest_handlers = true).
  - C++: Replacements: config field enumeration from the ConfigurableProcessor bind lists; a Creature::setAi(); an accessor for connections; a static color name table; a virtual/typeid simple name. The enum parse helper must throw a typed exception carrying enum name and values (magic_enum) instead of parsing messages. Point QuestSpawnAnalyzer at the C++ handler sources (the regex `\bsp(?:awn)?\(` still matches if call syntax is preserved), generate the npc id set at build time, or disable it.
- **Engines are initialised in parallel, reload swaps registries while other threads read them, and AI reload leaves old AI instances alive.**
  - Evidence: GameServer.java:100-101 `.parallel().forEach(GameEngine::init)`. ChatProcessor.reload (ChatProcessor.java:37-48) clears and refills a HashMap in use. AIEngine.reload clears aiHandlers ('NPCs must respawn to use the reloaded AI', Reload.java). Reload.java:51-102 reassigns DataManager.QUEST_DATA/SKILL_DATA/ITEM_DATA... at runtime.
  - C++: With compiled-in handlers the factory tables are immutable (built once, read-only, no lock). Only data-derived tables (quest event maps, command access levels, XML quests) need reload handling: build a new object and swap an atomic shared_ptr, as with ConfigValue<T>. Reloading ai/commands becomes a no-op or rebuild. Record this in DEVIATIONS.md.
- **With MSVC, self-registering static objects in a STATIC library are dropped, and the project's aion_add_library creates STATIC libraries.**
  - Evidence: cpp/cmake/AionCompilerOptions.cmake: `add_library(${target} STATIC ${sources})`. The MSVC linker only pulls an .obj out of a .lib to resolve an unresolved external symbol; a handler TU whose only effect is a registrar initializer is never referenced (standard MSVC/COFF behaviour, not tested here).
  - C++: Design 1 needs `add_library(... OBJECT)` or `$<LINK_LIBRARY:WHOLE_ARCHIVE,...>` (CMake ≥3.24, /WHOLEARCHIVE) for the server and for every test exe. Designs 2/3 avoid the problem because a table/function references each handler's factory symbol. Also avoid registrars that are static data members of class templates: they are only instantiated when odr-used.

## Risks
- 1. Object lifetime in delayed tasks and anonymous callbacks (highest risk; drives decision A). ~685 ThreadPoolManager uses plus 106 anonymous Runnables, 11 AIRequest and 7 ItemUseObserver callbacks capture AI `this`, Npc, Player, QuestState or WorldMapInstance. 117 AI files cannot cancel their tasks, and 17 instance handlers with tasks have no onInstanceDestroy. A literal port with raw pointers produces use-after-free that shows up only under timing (despawn, logout, instance destroy).
- 2. AI construction semantics. Creature.java:67 creates the AI inside the base constructor, and the Java reflection matches the most-derived owner class. C++ needs two-phase init, and the generic owner type needs a compile-time replacement. Getting this wrong silently gives NPCs DummyAI or a wrongly typed owner. `//ai set` swaps a final field at runtime.
- 3. All-or-nothing startup validation. AIEngine throws for any of 432 missing AI names, and ChatProcessor throws for any alias missing from commands.properties. Incremental porting needs explicit dev fallbacks, or the server cannot start until all 457 AIs are ported.
- 4. Build time and link mechanics for ~1,600 extra TUs. Handler TUs include heavy object-model headers (Player, Npc, packets, services). Unverified estimate: 1-3 s per TU in MSVC Debug → roughly 30-90 CPU-minutes for a full rebuild, i.e. several minutes wall-clock with /MP on 32 threads. PCH per category and unity builds help, but unity builds break on anonymous-namespace/registrar name collisions and `using namespace` leaks. STATIC libs drop self-registering objects.
- 5. Handler API surface. 484 distinct core classes are imported by handlers (admincommands alone 249, ai 262), so phase 6 cannot start before most of services/skillengine/world/network packets exist. Quests (76 imports) can start much earlier than admin commands.
- 6. Hidden reflection or JVM-message dependencies that would be missed in a mechanical port: ChatCommand.toErrorMessage parses Java exception text (ChatCommand.java:167-175), Id/Stat use getSimpleName, Configure enumerates config fields, Dye uses java.awt.Color names, Debug reads a private static field, and QuestSpawnAnalyzer scans .java sources.
- 7. JAXB inside handlers. Six handlers deserialize XML at runtime (4 consolecommands with private nested JAXB classes, Reload.java, Send.java with its own schema). The static-data generator (B) must expose loaders callable at runtime, or these need hand-written pugixml parsers.
- 8. Concurrency of shared registries. Engines init in parallel (GameServer.java:101), and QuestEngine maps and command maps are rebuilt by //reload while packet threads read them. Plain std::unordered_map replacement would be UB.
- 9. Name collisions. Duplicate simple class names (CalindiFlamelordAI x2, PadmarashkaAI x2) and admin commands named Event/Pet/Skill/SysMail/WorldRaid require strict package-mirroring namespaces and fully qualified names in any generated table.

Proposed porting order and partitioning:
1. Phase 4/5 (framework): registry infrastructure + generator; AI framework (src/ai) + the 43 root AI handlers (aggressive/general/noaction/... cover >85% of NPC templates); ChatCommand framework + ~10 debug admin commands (add, spawn, goto, level, ai, info, set, kill, moveto, reload); QuestEngine + AbstractQuestHandler + 16 XML quest templates (gives 4,184 quests without handler files); InstanceEngine/GeneralInstanceHandler; ZoneService handlers (3 files).
2. Phase 6 batches, most mechanical first: (a) quests by subdirectory (90 dirs, ~10 files/batch dir, disjoint files, same API); (b) world, siege, portal and event AIs by subdirectory; (c) instances as vertical slices: instance/<X>Instance.java + ai/instance/<x>/** together (43 AI instance dirs ↔ 73 instance handlers); (d) player and console commands; (e) remaining admin commands, including the reflection-heavy ones (Configure, Ai, Debug, Dye, Send, Reload) last.
3. At each step, count checks against Java expectations: 457 AI names, 73 instance ids, 5,219 quest handlers (1,035 + 4,184), 152 commands, 5 zone names. Keep a dev fallback for AI names not yet ported.

## Open questions
- Runtime counts could not be verified because no JVM runs are allowed. The expected 'Loaded N' values below come from source and XML analysis only: 457 AI handlers, 5,219 quest handlers, 73 instance handlers, 152 commands, 5 zone handler names.
- Build time is unverified: no C++ handler exists yet and no MSVC timing logs were found. The 1-3 s per handler TU estimate should be measured by porting ~20 quest and AI handlers against the real headers, with and without PCH/unity build, before choosing batch sizes.
- Should //reload ai and //reload commands survive? With compiled-in handlers they can only rebuild tables (commands: re-read access levels). //reload quests stays meaningful (XML quests), so the swap strategy for QuestEngine's 27 event maps has to be chosen.
- Handler source location and namespaces: mirror data/handlers under cpp/game-server/handlers/<category>/... with namespace aion::gameserver::handlers::<package>? This must avoid the duplicate simple names (CalindiFlamelordAI, PadmarashkaAI) and the clashes with core classes (Event, Pet, Skill, SysMail, WorldRaid).
- Partial-port policy: when an npc_template AI name has no handler (AIEngine.java:112-114) or a commands.properties alias has no command, should the server fall back with a warning (dev switch) or keep Java's hard error? Missing handlers are not an error for quests and instances in Java.
- Is a semi-automatic Java→C++ converter for the 1,035 quest handlers (uniform structure, 76 imports) worth building, versus hand/LLM batches? This depends on how closely the C++ AbstractQuestHandler API mirrors Java (same helper names and overloads).
- Task/lifetime API for handlers (ties to decision A): does ThreadPoolManager::schedule take an owner handle (weak_ptr/object id) so callbacks are dropped when the AI, instance or player is gone? Who cancels the 117 AI files' untracked tasks?
- QuestSpawnAnalyzer (default on): scan the C++ handler sources at runtime, generate the npc-id set at build time, or drop it?
- Should other core class-keyed registries use the same mechanism: client packet factory (190 CM_* classes, AionClientPacketFactory.java), skill effects (185 classes, EffectType derived from class simple name in Effects.java:182), XML polymorphic templates (29 @XmlElements/@XmlSeeAlso sites)? Not analysed in depth here.

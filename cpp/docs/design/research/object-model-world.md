# object-model-world

## Summary
The Java game object model is a free-threaded, GC-reliant graph. AionObject (objectId, equals/hashCode by objectId) is the root of about 42 classes. VisibleObject has 33 descendants (Creature 11, Npc 8, SummonedObject 6, HouseObject 12). Each VisibleObject is a composition of per-object parts that point back at it: controller, KnownList, AI, EffectController, ObserveController, AggroList, Game/LifeStats and MoveController. Those internal cycles are harmless. The hard part is the cross-object references: KnownList entries (two-way), target, AggroInfo.attacker, Effect.effector/effected, Skill.effector/effectedList, Summon/Pet.master, SummonedObject.creator, Player.summon/pet/kisk/postman/playerGroup, team members (PlayerTeamMember.player), DropNpc player collections, handler fields (e.g. `Npc boss`, `List<Npc>`), queued server packets, and about 850 scheduled-task call sites (724 schedule plus 125 scheduleAtFixedRate; 679 of them in data/handlers) that capture objects, usually `this` of an AI or controller. Most cross references are cleared by explicit lifecycle hooks: World.despawn → KnownList.clear (both sides) → CreatureController.notKnow → AggroList.remove, CreatureController.onDespawn → aggroList.clear, onDelete → cancelAllTasks, and NpcController.onDespawn → removeAllEffects on the npc itself. Several important references are never cleared and rely on the GC keeping stale objects readable. (1) Effects an npc applied to others survive its deletion; NpcController.java:294 explicitly handles a despawned attacker from a DoT. (2) Groups and alliances keep logged-out Player objects for 600 s by default. (3) Periodic tasks end themselves by checking `!owner.isInWorld()` or `!isSpawned()` on the captured object. (4) Handlers check `isDead()`/`isSpawned()` on captured owners after delays; 102 schedule sites in ai/instance handlers do so within a few lines. (5) EmpyreanCrucibleInstance compares stored, possibly deleted Npcs by objectId equality. The most important hidden invariant is in AionObject.java:31: object IDs of npcs, summons, teams and so on are released to IDFactory by a java.lang.ref.Cleaner only after the object is garbage collected. As a result, objectId equality and ID-keyed lookups can never confuse a stale object with a newer one while anyone still holds it. There are only 3 weak-reference uses in total (Cleaner, one WeakReference in DropNpc, one WeakHashMap in InstanceScaler). Threading has no game loop or per-object serialization: 4 packet processor threads, scheduled and instant pools (at least 4 threads each), a ForkJoin parallelStream in MoveTaskManager, and NIO threads that serialize packets lazily and read live object state. Concurrency relies on ConcurrentHashMap weakly consistent iteration (238 src sites), about 235 synchronized/lock sites in src, and ad-hoc Atomic* flags (311 in handlers). Players are re-instantiated from the DB on every login, keep the same DB objectId, and so compare equal to their stale previous instances. This evidence favours intrusive reference counting with ID release in the final destructor (an exact analogue of the Cleaner) over pure handle/ID lookups. A pure handle scheme would change the semantics of hundreds of handler sites and the team, effect and packet code.

## Lifecycle states
1. Constructed, not in World (two-phase init; ClusteredNpc walkers stay here until organizeAndSpawn: VisibleObjectSpawner.java:62).
2. Stored, not spawned (`isInWorld()` true, `isSpawned()` false): between storeObject and spawn, during teleport (despawn→setPosition→spawn), players during enterWorld.
3. Spawned (in MapRegion, instance maps, knownlists, zones).
4. Dead but spawned (corpse): state DEAD, AI DIED, knownlist and aggro kept until DECAY (2 s, or 5 min with drop).
5. Despawned (still stored).
6. Deleted (World.removeObject → onDespawn + onDelete → cancelAllTasks). The object is still referenced by effects, team membership, handler fields, pending lambdas (including cancelled ScheduledFutures, which stay queued until their delay because setRemoveOnCancelPolicy is never set) and queued packets.
7. Garbage-collected: the Cleaner releases the objectId unless RespawnService.setAutoReleaseId defers it to respawn completion.
Player-specific states: online (clientConnection != null); semi-offline and still spawned for up to 10 s after a disconnect (DESPAWN task, AionConnection.onDisconnect:254); logged out but kept as a stale member of a group/alliance for up to 600 s; relogin creates a new Player with the same objectId (PlayerService.java:106).

## Key findings
- **Object IDs are released only when the Java object is garbage collected (Cleaner), not when it is deleted from the world. This makes objectId-based equality and ID-keyed maps safe against stale objects.**
  - Evidence: model/gameobjects/AionObject.java:17,31-34: CLEANER.register(this, () -> { if (!RespawnService.setAutoReleaseId(objId)) IDFactory.releaseId(objId) }). Used with autoReleaseObjectId=true by Npc (Npc ctor calls IDFactory.nextId(), super(...,true)), Summon, HouseObject, GeneralTeam/TemporaryPlayerTeam. World.java:93 javadoc states it. equals/hashCode are final and objectId-based (AionObject.java:47-63). RespawnService.java:95-101 and RespawnTask.setReleaseIdOnCompletion defer release while a respawn is pending.
  - C++: Release the ID in the destructor of the last reference: refcount reaching zero is the direct analogue of the Cleaner. Keep the RespawnService deferral hook. A handle/ID-lookup design would instead need generation counters, because IDs could be reused while old IDs are still stored (pendingRespawns, DropNpc, handler fields).
- **Code relies on deleted or despawned objects staying readable and self-checks liveness on the captured object instead of cancelling.**
  - Evidence: LifeStatsRestoreService.java:53,72 (periodic task ends itself when !owner.isInWorld()); MoveTaskManager.java:40-46 (!isSpawned self-heal); NpcController.java:84 (a 750 ms lambda capturing the controller calls getOwner().getAi().think()); handlers: YamenessPortalSummonedAI.java:27,32 (isDead() || !getOwner().isSpawned() 'instance is not destroyed yet'); 102 schedule sites in ai/instance handlers check isDead/isSpawned/isInWorld within 6 lines; EmpyreanCrucibleInstance.java:53-58 keeps List<Npc> stageNpcs and tests liveness by npc.equals(stageNpc) against instance.getNpcs(); getController().delete() is idempotent (World.removeObject returns false if not stored) and is called 342 times in handlers.
  - C++: Pure weak handles (lookup returns null after delete) would force hundreds of handler sites to be rewritten and would change behaviour, for example tasks that still read the position of a dead or deleted owner. Strong refcounted references held by tasks, fields and packets keep the Java semantics. delete() must remain idempotent and safe on already-deleted objects.
- **Effects outlive their effector and are not removed when the effector is deleted; DoTs from despawned creatures keep ticking.**
  - Evidence: skillengine/model/Effect.java:39-40 final effector/effected; endTask lambda at :682 and periodicActionsTask at :871 capture Effect.this. NpcController.onDespawn removes only the npc's own effects (owner.getEffectController().removeAllEffects()). NpcController.java:294 comment: 'summon should gain its own aggro (except if despawned, for example because of a damage over time effect)'. Skill.java:663 schedules applyEffect(effects) after hitTime, then Effect.java:640 checks effected.isSpawned().
  - C++: Effect must hold a strong ref to the effector (or a stale-but-valid snapshot). A weak_ptr effector would need null checks at every getEffector() call in about 177 EffectTemplate subclasses.
- **Teams keep logged-out Player objects for up to 10 minutes. A new Player instance with the same objectId replaces them on relogin, and equals() treats old and new as the same.**
  - Evidence: PlayerTeamMember.java:10 `final Player player`; PlayerGroupService.java:210-222 OfflinePlayerChecker removes members only after GROUP_REMOVE_TIME (config/main/group.properties:8 = 600 s); alliance equivalent at PlayerAllianceService.java:277 (ALLIANCE_REMOVE_TIME 600); group/events/PlayerConnectedEvent.handleEvent: removeMember(id) then addMember(new PlayerGroupMember(player)); PlayerLeaveWorldService.java:65 setClientConnection(null) makes the player 'semi-offline', and PacketSendUtility.sendPacket (line 74-77) silently skips. PlayerService.java:106 creates a new Player on each login.
  - C++: An offline Player object must stay alive and readable (name, level, race, position, commonData) while a team holds it, so team membership needs a strong ref or a detached member snapshot. Object equality must stay objectId-based. The TOCTOU `isOnline()` then `getClientConnection()` in sendPacket must be made atomic (load the connection pointer once).
- **Most cross-object references are already cleared deterministically by despawn/delete hooks, so strong references rarely form permanent cycles.**
  - Evidence: World.despawn (World.java:312) → controller.onDespawn, region/instance removal, revalidateZones after isSpawned=false, then KnownList.clear (KnownList.java:51) removes both sides → CreatureController.notSee clears target, notKnow (CreatureController.java:77) → AggroList.remove; CreatureController.onDespawn (line 547-556) cancels DECAY, aborts move, clears the aggro list (which cancels hateReductionTask); onDelete (line 425) cancels all controller tasks; NpcController.onDespawn clears observers, effects and drops, and fires the instance handler and AI DESPAWNED; PlayerLeaveWorldService releases the summon and deletes pet/postman.
  - C++: With refcounting, keep these hooks as the cycle breakers and document them as invariants (after delete: knownlist empty, aggro empty, controller tasks cancelled, own effects ended). Remaining retention (effects on others, teams, handler fields, pending tasks) is bounded by task or effect duration. Add a debug registry of 'deleted but still alive after N minutes' objects to find leaks, the C++ counterpart of Java's silent GC.
- **Internal part-whole cycles are everywhere, but they are pure composition with back-pointers.**
  - Evidence: VisibleObjectController.owner (set via setOwner), KnownList.owner, AbstractAI.owner (AbstractAI.java:33), EffectController.owner, AggroList.owner, CreatureGameStats/LifeStats.owner, CreatureMoveController.owner, Equipment/FriendList/Mailbox/TitleList/MotionList/NpcFactions/PortalCooldownList.owner (Player parts). Creature.ai is final.
  - C++: Hold parts as unique_ptr members (or by value) with a raw back-pointer. Parts must forward reference counting to the owning object: a task capturing an AI or controller `this` (e.g. `this::spawnSummons` in 218 AI files) must keep the owning Creature alive, which intrusive counting on the owner does naturally.
- **`this` and getOwner() are passed into packets, events, tasks and collections from raw call contexts everywhere.**
  - Evidence: handlers: ~1,566 getOwner() uses; e.g. NpcController.onDie `new SM_EMOTION(getOwner(), ...)`, `new QuestEnv(getOwner(), player, 0)`; 80 of 232 server packets store object fields; AbstractAI.spawn returns VisibleObject; team events store Player/team fields (48 direct fields in model/team).
  - C++: std::shared_ptr would need enable_shared_from_this (a weak lock per conversion) and would push shared_ptr parameters into every signature. An intrusive refcount (atomic count in AionObject, a Ref<T> smart pointer constructible from T*) lets `Ref<Npc>(this)` be created anywhere. Convention: borrowed params as T&/T*, stored fields, captures, containers and packets as Ref<T>.
- **Server packets are serialized lazily on the network thread and read live game-object state; one packet instance can be queued to many connections.**
  - Evidence: AionConnection.java:204-213 writeData pops the packet from sendMsgQueue and calls packet.write(this, data) under guard; SM_NPC_INFO.writeImpl:47-56 reads npc.getX(), getMoveController() at write time; 24 server packet classes use `con.` in writeImpl. The C++ commons AConnection.h:231-237 keeps a queue of shared_ptr<TServerPacket> written on the strand, and CONVENTIONS.md 'Network packets' says one packet instance may be broadcast.
  - C++: Packets holding raw Npc*/Player* would dangle when an object is deleted while packets are queued. Either packets hold Ref<T> (keeps Java semantics, including cross-thread reads of positions), or the 80 object-holding packets snapshot their data in the constructor. Snapshotting is safer for data races but changes semantics slightly; the 24 connection-dependent packets still need per-connection write.
- **The concurrency model is free-threaded with no per-object or per-map serialization. Correctness depends on ConcurrentHashMap weakly consistent iteration and ad-hoc synchronization.**
  - Evidence: MoveTaskManager.java:40 parallelStream over moving creatures (ForkJoin common pool); KnownList.update is synchronized on its own list but calls newObject.getKnownList().add(owner) (KnownList.java:192) without the other lock; CollectionUtil.forEach iterates CHM values while others mutate; AbstractAI synchronizes only setStateIfNot/setThinking; synchronized-block targets are mostly `this` (40) and fine-grained fields (equipment 11, restoreLock 8, queuedSkills 5, observers 5, zoneTypes 4); only 2 locks on a game object (World.removeObject `synchronized(object)`, HousingService `synchronized(house)`); EffectController uses a StampedLock; GeneralTeam a ReentrantLock; handlers use 311 Atomic* and 139 cancel(true) (thread interrupt).
  - C++: Reference counts must be atomic. The C++ port needs a concurrent map with safe iteration under concurrent modification: a mutex-guarded map with snapshot iteration (copying Refs, so refcount traffic), or a library (e.g. a sharded or parallel hash map). cancel(true) cannot interrupt; map it to a cancel flag. The threading model (keep free-threaded vs. strands per map instance) is a separate decision, but it constrains ownership: stale-reference reads across threads are only memory-safe if objects are kept alive by refs.
- **Already ID-based references exist and can remain ID-based.**
  - Evidence: Npc.creatorId with World.findVisibleObject (Npc.java:318); RespawnService DecayTask(objectId) (RespawnService.java:134-148) and RespawnTask.oldObjectId; Legion.memberIds (Legion.java:28); Kisk.kiskMemberIds; WorldMapInstance.registeredObjects `Set<Integer>`; client packets resolve targets via knownlist getObject(id) (22 sites); World.getPlayer(int/name) 91 sites; handlers use instance.getNpc(npcId) 302 times.
  - C++: Keep these as IDs. They show the Java authors used IDs where objects are re-created (respawn, relogin), so no new handle abstraction is needed for them.
- **There are almost no weak references; GC also reclaims two map entries implicitly.**
  - Evidence: Weak/soft/phantom/Cleaner usage in src + data/handlers: AionObject.java:17 Cleaner; DropNpc.java:28 WeakReference<TemporaryPlayerTeam> lootingTeam (fallback to lastLootGroupRules); services/instance/InstanceScaler.java:25 Collections.synchronizedMap(new WeakHashMap<WorldMapInstance, Scaling>()) with no explicit removal. None in handlers.
  - C++: InstanceScaler needs explicit removal in InstanceService.destroyInstance (InstanceService.java:82-107). DropNpc can hold a team ID or weak ref. No other code expects weak semantics.
- **Deletion paths do not cancel everything that captures the object; Java's scheduler also keeps cancelled tasks, with their captured objects, until their delay expires.**
  - Evidence: AggroList.hateReductionTask is cancelled only in clear(); CreatureLifeStats.lifeRestoreTask is cancelled on logout (PlayerLeaveWorldService.java:113) but for npcs only by self-check; AI lambdas scheduled without addTask are not cancelled on delete (only 96 of 218 scheduling AI files cancel in handleDied/handleDespawned); InstanceService.destroyInstance deletes objects then calls handler.onInstanceDestroy (28 of 43 scheduling instance handlers override it); setRemoveOnCancelPolicy is never called (grep over game-server/src and commons/src).
  - C++: C++ tasks must tolerate running against deleted objects, as in Java, with the object kept alive by the task's Ref. The C++ scheduler should destroy the callable on cancel (better than Java, frees refs and IDs early). The ID-release timing then differs harmlessly.
- **Spawn and instance teardown order means stale objects keep references to destroyed WorldMapInstances.**
  - Evidence: WorldPosition.mapRegion (WorldPosition.java:25) is not nulled on despawn; MapRegion.parent → WorldMapInstance; InstanceService.destroyInstance removes the instance from WorldMap, then deletes the objects, then onInstanceDestroy; World.createPosition throws NullPointerException for an invalid instanceId (World.java createPosition); handlers guard spawn() with isSpawned() for this reason (YamenessPortalSummonedAI.java:27).
  - C++: Either WorldPosition/MapRegion hold a Ref to the WorldMapInstance (instances then live as long as any stale object), or positions store mapId/instanceId plus a region pointer that is valid only while spawned. The former matches Java; memory cost is bounded by task lifetimes.

## Risks
- Stale-reference semantics in handlers (highest risk). About 679 lambdas scheduled in data/handlers capture AI `this` or Npc/Player objects, 102+ of them re-check isDead/isSpawned on the captured object, and 342 call delete() on possibly deleted objects. Any ownership scheme that frees on delete (unique_ptr in World, or handles that return null) turns these into use-after-free or null dereferences across 1,700 mechanically ported files. Mitigation: refcounted Ref<T> captured by tasks.
- Data races made memory-unsafe. Java tolerates racy reads (NIO thread serializing SM_NPC_INFO while MoveTaskManager's ForkJoin threads move the npc; KnownList.update mutating the other side's list; isOnline()/getClientConnection() TOCTOU). The same races in C++ on non-atomic fields (float x/y/z, pointers) are undefined behaviour. Porting the free-threaded model 1:1 needs atomics or locks on hot fields, or a threading redesign (strands per map instance) that ripples into ownership.
- ConcurrentHashMap weakly consistent iteration has no std equivalent. 238 src sites plus KnownList, MapRegion, WorldMapInstance, AggroList, World and team maps are iterated while being modified from other threads (CollectionUtil.forEach). A snapshot-copy approach costs allocations and refcount increments in the hottest loops (knownlist broadcasts, MovementNotifyTask).
- Cycle leaks with refcounting. Npc → CreatureController.tasks → Future → lambda → Npc is broken only if tasks are cancelled or run; AggroList.hateReductionTask is cancelled only via clear(); Effect effector/effected pairs; Summon.master ↔ Player.summon; team ↔ Player.playerGroup; KnownList two-way entries if a despawn hook throws (World.removeObject catches and logs 'did not leave world cleanly'). Java's GC hides these leaks; C++ needs a leak tracker and scheduler semantics that drop callables on cancel/completion.
- Object ID reuse. If IDs are released on delete instead of on last-reference drop, objectId equality (AionObject.equals), ID-keyed maps (pendingRespawns, DropRegistrationService, KiskService, knownObjects) and stored-Npc liveness checks (EmpyreanCrucibleInstance.java:55) can alias a new object.
- Two-phase initialization and virtual calls in constructors. Npc ctor calls setupStatContainers() (virtual; Servant/Trap/Homing/SummonedObject override it) and controller.setOwner(this); knownlist and effect controller are set after construction. In C++, virtual calls in constructors do not dispatch to derived overrides, so the factory functions in VisibleObjectSpawner must perform post-construction init.
- Generic self-typed hierarchies (VisibleObjectController<T extends VisibleObject>, CreatureGameStats<T>, AbstractAI<T>, SummonedObject<T>, HouseObject<T>, GeneralTeam<M,TM>) with covariant getOwner()/getController() overrides in about 42 object classes and 462 AI classes. They map to CRTP or static_cast accessors, but a mistake is silent UB.
- Lazy packet serialization. The 80 object-holding server packets must either hold refs, which keeps objects alive while queued and adds cross-thread reads, or snapshot in the constructor, which changes semantics and needs care for the 24 connection-dependent writeImpl bodies.
- Future.cancel(true) (139 in handlers) interrupts running tasks in Java; C++ cannot, so long-running or looping tasks that rely on interruption need explicit cancel flags.
- Multi-client stale Player instances. Relogin creates a new Player with an equal objectId while the old instance may still be referenced by teams, effects, DropNpc or tasks. Any code comparing by pointer identity instead of objectId changes behaviour (World.removeObject deliberately uses identity: World.java:103-106).

## Dependencies
What the object model/world core depends on, and must exist at least as interfaces before it compiles:
- Static data templates: VisibleObjectTemplate/NpcTemplate/CreatureTemplate, SpawnTemplate (plus Rift/Siege/Vortex/Base/Town/AhserionsFlight variants), WorldMapTemplate (World ctor iterates DataManager.WORLD_MAPS_DATA), ZoneTemplate/ZoneInfo (WorldMapInstance ctor → ZoneService.getZoneInstancesByWorldId), TribeRelations, SkillTemplate, KiskStatsTemplate, housing templates. These come from decision (B) and must land first.
- IDFactory (Npc ctor calls IDFactory.nextId(); release in the Cleaner, i.e. the destructor).
- ThreadPoolManager-equivalent scheduler with cancellable futures (850 call sites), plus AbstractPeriodicTaskManager/FIFO managers (MoveTaskManager, MovementNotifyTask, ZoneUpdateService).
- GeoService (VisibleObjectController.onBeforeSpawn/onDespawn for static IDs, AggroList canSee, spawnPostman) and geo data.
- AIEngine/AbstractAI (Creature ctor creates the AI; spawn/despawn/die fire AI events), so the AI framework skeleton is needed with the object model.
- skillengine: Effect, EffectController, Skill (Creature fields and CreatureController.onDie/onAttack), plus stats containers (CreatureGameStats/LifeStats and subclasses).
- QuestEngine (WorldMapInstance.addObject queries getQuestNpc; NpcController rewards), InstanceHandler interface (WorldMapInstance ctor takes a handler supplier; onDie/onDespawn/onStartEffect hooks), DropService/DropRegistrationService, RespawnService, RiftService, EventService, SiegeService (localSiegeNpcs), InstanceScaler.
- Network: AionConnection (Player.clientConnection), PacketSendUtility and about 80 SM_ packets that take objects, plus CM_ packets resolving objects by ID.
- DAOs: PlayerDAO, PlayerEffectsDAO, ItemCooldownsDAO, PlayerLifeStatsDAO and others in PlayerService/PlayerEnterWorldService/PlayerLeaveWorldService.

What depends on it: virtually everything else. Services (169 top-level files), skillengine (177 EffectTemplate subclasses operate on Creature/Effect), questEngine, all 1,729 handler files (457 AI classes, 1,052 quests, 80 instances, 157 commands), about 240 server packets and 190 client packets, and team/legion/housing/siege/vortex systems.

Suggested order implied by the graph (for the partitioning decision):
1. Ownership primitives (Ref<T>, intrusive count in AionObject, ID release in destructor), scheduler with Ref-capturing tasks, concurrent map and snapshot iteration utilities.
2. Static templates needed by the world (world maps, zones, npc/spawn templates).
3. 5. Stats/skills/effects and the AI framework → fight a mob.

## Open questions
- How many objects are alive at runtime (world maps spawned at startup plus typical instances)? The only static estimate is about 131,896 `<spot` entries under data/static_data/spawns (including instance and event templates not spawned at once). A live count would size the ID/handle table and show the refcount overhead, but it cannot be measured without running the Java server (no JDK by decision).
- Should the free-threaded Java model be kept (atomics and locks on hot fields, concurrent maps) or should game logic be serialized, e.g. one strand per WorldMapInstance plus a global strand for cross-instance services? This interacts strongly with decision (A); teleport, teams, siege and chat cross instances. Not analyzed in depth here.
- Should the 80 object-holding server packets snapshot data at construction (removing cross-thread reads) or hold Ref<T> and serialize lazily as in Java? Which of them depend on reading state at write time or on the target connection (24 use `con.` in writeImpl)?
- Reference identity (==) vs objectId equals: World.removeObject deliberately uses identity (World.java:103-106) to reject a different instance with the same ID. The number of other identity comparisons between game objects (e.g. `getTarget() == x`) was not quantified; those with stale-Player semantics would need auditing.
- Do any handler or service paths rely on cancel(true) interrupting a running task (139 handler sites), or is cancel(true) only used as 'cancel if not started'? Not verified per site.
- Can WorldPosition keep a strong reference to a destroyed WorldMapInstance, which retains MapRegions, zones and the instance handler, or should instance teardown sever it? This depends on how often stale objects outlive instance destruction (instance handlers with uncancelled tasks: 15 of 43 scheduling instance files do not override onInstanceDestroy).
- Are there exception paths in World.removeObject/despawn ('did not leave world cleanly', World.java:109) that leave knownlist or aggro references uncleared? Refcounting would turn those into leaks.
- Class counts come from a regex scan of `class X extends Y` and miss some generic declarations with nested angle brackets (e.g. TemporaryPlayerTeam, whose subclasses were added manually). Exact counts would need a Java parser.
- The field census is regex-based (class-level fields with 1-tab indentation or explicit modifiers). Local variables were excluded but anonymous-class fields may be under-counted, and lambda captures were only counted at the call-site level, not per captured object.

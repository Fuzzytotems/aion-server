# network

## Summary
The game server's network package (D:\aion-server\game-server\src\com\aionemu\gameserver\network) is about 59k Java lines in 515 files. Half of that is SM_SYSTEM_MESSAGE.java: 28,958 lines holding 4,119 generated static factories. The rest is 237 mapped server packets (240 files), 186 mapped client packets (190 files), the crypt, and the connections to the login server (11 CM, 14 SM) and chat server (2 CM, 4 SM). The game client cipher is completely different from the login server's Blowfish/RSA scheme. It is a small stateful XOR stream cipher: a 64-byte static key plus an 8-byte per-direction key that grows by the packet size after each packet. The first server packet, SM_KEY, goes out unencrypted, and opcodes are obfuscated using INTERNAL_VERSION 207. It is about 190 lines, easy to port and to unit-test with an inverse client implementation.

The finding that matters most for design decisions A and B: server packets are built LAZILY. Constructors mostly store references, and writeImpl reads live game-object state later, on the NIO write thread, when the packet leaves the queue. About 63 packets hold Player/Creature/Item/Effect/... references that writeImpl reads. 25 more depend on the recipient connection (con.getActivePlayer()). 10 read global services or configs at write time. About 20 more hold collections of mutable game data. Only about 120 of 237 are plain value packets. The Java server gets away with this because it forces exactly one NIO read/write thread ("the game server is not thread-safe", GameServer.java:197). The same packet instance is also queued to many connections by broadcasts, and Java's per-packet `buf` field is only safe with that single thread. Six packets even change game state inside writeImpl (SM_ATTACK, SM_CASTSPELL_RESULT, SM_PET, SM_PLAY_MOVIE, SM_GROUP_MEMBER_INFO/SM_ALLIANCE_MEMBER_INFO). In C++, keeping this lazy model means cross-thread reads of std::vector/std::string state, which is undefined behaviour, and packets extending object lifetimes. My recommendation is to serialize the plaintext body when sendPacket is called, on the calling thread. That means once per packet for recipient-independent packets and once per recipient for the 25 that depend on the connection. Queue the bytes, and encrypt per connection on the strand. Queued packets then never keep game objects alive, which removes one GC-reliant reference pattern from decision A.

The connection state machine is simple: CONNECTED, AUTHED, IN_GAME. Allowed states are checked twice, when the packet is created in the factory and again before runImpl. 167 of 186 client packets are IN_GAME-only. Client packets are thin: readImpl averages about 6 lines, runImpl about 16 lines (3,011 in total), and they mostly call services. They should be ported together with the services they call. Server packets can be ported earlier, against the model getters. The login and chat server links are outbound AConnections with fixed reconnect delays: 10s/60s after a failed connect, 5s (was authed) or 15s after losing the connection. Their incoming packets run unordered on the general thread pool. Everything here was checked by reading and grepping only; no Java was run (no JDK).

## Opcode tables
- Client: `PacketInfo[250]` array indexed by decoded opcode (AionClientPacketFactory.java:24). 186 entries. Built with reflection (`getConstructor(int, Set)`).
- Server: `HashMap<Class, Integer>`, 237 entries, highest opcode 303 (ServerPacketsOpcodes.java:321). Each packet constructor looks up its opcode by `getClass()` (AionServerPacket.java:33).
- Allowed states per client packet: IN_GAME 167, AUTHED 10, AUTHED+IN_GAME 4, CONNECTED 2 (CM_VERSION_CHECK, CM_L2AUTH_LOGIN_CHECK; CM_MAC_ADDRESS is also CONNECTED-only), all three states 2 (CM_TIME_CHECK, CM_SECURITY_TOKEN).
- LS link: 1-byte opcodes, HashMap factory, states CONNECTED/AUTHED. CS link: same pattern, 2 client packets.

## Wire format (game client)
- Server frame: `[u16 len incl. itself][u16 (op+207)^0xDF][u8 0x44][u16 ~obfOp][body]`. Everything after `len` is encrypted (AionServerPacket.java:43-69).
- Client frame: `[u16 len][u16 obfOp][u8 0x65][u16 ~obfOp][body]`. Decoded opcode = `(((op^0xEF)-0xC)^0xEF)-207` (Crypt.java:89-91). Valid only if short(0)==~short(3) and byte(2)==0x65 (EncryptionKeyPair.java:92-94). There is no padding and no checksum, unlike the login server.
- Size limits: read and write buffers are 32,768 bytes (AionConnection.java:109). The client only accepts 8,192 bytes (MAX_CLIENT_SUPPORTED_PACKET_SIZE), and MAX_USABLE_PACKET_BODY_SIZE is 8,185. A larger packet only logs a warning after it was written (AionConnection.java:217). `DynamicServerPacketBodySplitList`/`FixedElementCountSplitList` split lists into several packets (8 callers).

## Crypt (vs login server)
| | Game server (Crypt/EncryptionKeyPair) | Login server (already ported: ncrypt/CryptEngine, Blowfish, RSA) |
|---|---|---|
| Cipher | Rolling XOR: `b[i] ^= static[i&63] ^ key[i&7] ^ prevCipherByte` | Blowfish ECB + checksum + 8-byte padding; RSA session setup |
| Key | 8 bytes = LE(random int) + A1 6C 54 87, same start for both directions; after each packet the 64-bit key += packet size (client key only after a valid decrypt) | Blowfish key sent in SM_INIT |
| Key exchange | SM_KEY (opcode 72) sends `(key ^ 0xCD92E4DF) + 0x3FF2CCCF`; `enableKey()` runs inside SM_KEY.writeImpl at write time; the first encrypt() call only sets isEnabled (Crypt.java:69-77) | |
| Before the key | Client data is dropped silently until SM_KEY has been written (AionConnection.java:151) | |
| Errors | Up to 3 failed decrypts tolerated, then disconnect (AionConnection.java:154-161); fewer than 5 bytes after decrypt = disconnect | Checksum failure = disconnect |

## Key findings
- **Server packets are lazy. Most packets with object state store references in the constructor and read live game state in writeImpl, which runs on the NIO thread when the packet is dequeued. That can be much later if the client's socket is backed up.**
  - Evidence: 63 packets hold game-object references that writeImpl reads, e.g. SM_PLAYER_INFO(Player) reads position, appearance, legion, equipment, move controller and team (SM_PLAYER_INFO.java:41-227). SM_NPC_INFO(Creature) (:47-129), SM_MOVE(Creature), SM_INVENTORY_INFO(List<Item>, Player) builds ItemInfoBlob at write time (:52-53), SM_ABNORMAL_EFFECT(Collection<Effect>) reads effect.getRemainingTimeToDisplay() at write. The Java Dispatcher.write calls con.writeData once per packet only when the socket is writable (Dispatcher.java:230-270).
  - C++: A faithful lazy port needs packets to keep game objects alive (shared_ptr or handles) and reads game-thread-mutated containers from the IO strand, which is undefined behaviour in C++. Prefer eager serialization: in sendPacket, run writeImpl(con, buf) on the calling thread into a byte vector, queue the bytes, and do only framing and encryption on the strand. Queued packets then never reference game objects, and decision A does not need 'packet keeps object alive' semantics.
- **The Java game server only runs with a single NIO read/write thread, because lazy packets are not thread-safe.**
  - Evidence: GameServer.java:197-198 throws `gameserver.network.nio.threads must not exceed 1 (the game server is not thread-safe)`. network.properties:41-42 has an `unsafe.allow` flag. BaseServerPacket.java:15 has a public mutable `ByteBuffer buf` set per write, shared by the same instance queued to many connections through PacketSendUtility.broadcastPacket (:98-100).
  - C++: The C++ commons NioServer runs N IO threads, and BaseServerPacket already has no buffer member. If writeImpl stays lazy, the game server must use 1 IO thread and still accept cross-thread reads against the game logic threads. With eager serialization, N IO threads are safe.
- **25 server packets depend on the recipient connection. Several of them are broadcast, so one instance produces different bytes per recipient.**
  - Evidence: con.getActivePlayer() used in 24 packets, con.getAccount() in 2, con.enableCryptKey() in 1. SM_PLAYER_INFO.java:37-45 computes race per viewer (enemy/neutral). SM_MESSAGE.java:136-138 blanks race obfuscation for staff viewers. SM_DIALOG_WINDOW, SM_PRICES, SM_LOOT_ITEMLIST, SM_SIEGE_LOCATION_INFO, SM_HOUSE_OBJECT, SM_CHARACTER_LIST and others. Full list: SM_ACCOUNT_PROPERTIES, SM_ALLIANCE_INFO, SM_BLOCK_LIST, SM_CHALLENGE_LIST, SM_CHARACTER_LIST, SM_DIALOG_WINDOW, SM_FRIEND_LIST, SM_FRIEND_UPDATE, SM_GROUP_INFO, SM_HOUSE_BIDS, SM_HOUSE_EDIT, SM_HOUSE_OBJECT, SM_HOUSE_REGISTRY, SM_INSTANCE_INFO, SM_KEY, SM_LOOT_ITEMLIST, SM_MAIL_SERVICE, SM_MARK_FRIENDLIST, SM_MESSAGE, SM_PLAYER_INFO, SM_PLAYER_SEARCH, SM_PLAY_MOVIE, SM_PRICES, SM_SIEGE_LOCATION_INFO, SM_UNK_3_5_1.
  - C++: Mark packets as connection-dependent, e.g. `virtual bool dependsOnConnection() const` or two writeImpl signatures. A broadcast serializes connection-independent packets once and shares the plaintext (shared_ptr<const vector>), and serializes connection-dependent ones per recipient. Encryption is per connection in any case.
- **Six packets change game or packet state inside writeImpl, so their side effects happen at write time.**
  - Evidence: SM_ATTACK.java:89 and SM_CASTSPELL_RESULT.java:181 call `Player.setLastCounterSkill` ('best synchronization of time with client'). SM_PET.java:219,227-228,233,240 set pet mood/gift cooldowns. SM_PLAY_MOVIE.java:28 `con.getActivePlayer().setCustomState(WATCHING_CUTSCENE)`. SM_GROUP_MEMBER_INFO.java:54 and SM_ALLIANCE_MEMBER_INFO reassign their own `event` field. SM_KEY enables the connection crypt.
  - C++: With eager serialization these side effects move to send time, a small and arguably more deterministic timing change; list it in DEVIATIONS.md. writeImpl cannot be `const` for these six; move the side effects into the constructor or the send path. SM_KEY must stay special: its write-time effect on the crypt has to remain on the strand.
- **The game client crypt is a small XOR stream cipher with rolling per-direction keys. It shares nothing with the login server's Blowfish/RSA code.**
  - Evidence: EncryptionKeyPair.java:27 has a 64-char static key; :58-59 initial key LE(rnd) + A1 6C 54 87; :102-144 decrypt (key += size only if validated); :150-187 encrypt (key += size always). Crypt.java:50 enciphers the key sent in SM_KEY; :82-91 opcode obfuscation using INTERNAL_VERSION=207 (SM_VERSION_CHECK.java:21). The static bytes are 0x44 (server) and 0x65 (client). AionServerPacket.java:66 encrypts the slice after the length short.
  - C++: Port it as its own class with uint8_t/uint64_t arithmetic. Java long wraps; C++ must use unsigned. Keep the operator precedence of `(op ^ 0xEF) - 0xC ^ 0xEF`, which C++ shares, but add parentheses. The crypt state is only touched on the strand (processData, writeData), so no locks are needed. Test with an inverse client-side implementation and golden vectors, like the login server. The 3-strike decrypt tolerance and 'drop input before SM_KEY is written' must be kept.
- **The packet flood filter is simple but its behaviour contradicts its documentation, and its example opcode is out of date.**
  - Evidence: AionConnection.java:173-186: per-connection ConcurrentHashMap opcode → last receive time, checked before read(). `if (PffConfig.PFF_MODE == 1) return false` disconnects in mode 1, but pff.properties documents 1 = log and 2 = log + disconnect, default mode = 1. The @Properties map is never null (ConfigurableProcessor.java:135-137), so the map is allocated for every connection when mode > 0 even with no thresholds configured. The example `0x0C4 # CM_CASTSPELL` is stale: CM_CASTSPELL is opcode 33, and 196 (0xC4) is CM_SHOW_MAP (AionClientPacketFactory.java:61,224). FloodManager (connection-rate filter, off by default) uses a static java.util.Timer via NetFlusher.
  - C++: Port as Java behaves (mode 1 disconnects) and record it, or fix it and list the fix in DEVIATIONS.md. Bind THRESHOLD_MILLIS_BY_PACKET_OPCODE with bindPattern and hex keys. Allocate the per-connection map only when the threshold map is non-empty. Replace NetFlusher's Timer with the server scheduler.
- **Connection and Player reference each other, and a disconnected connection stays referenced for up to 10 seconds.**
  - Evidence: Player.clientConnection (Player.java:270-280) and AionConnection.activePlayer (AionConnection.java:91). On disconnect: leaveWorldDelayed(player, max(0, 10s - sinceLastPacket)) (AionConnection.java:251-254). leaveWorld clears both links (PlayerLeaveWorldService.java:65,152). LoginServer holds loginRequests/loggedInAccounts maps of AionConnection (LoginServer.java:44-45). ConnectionAliveChecker captures `this` in a 180 s fixed-rate task. PacketSendUtility.sendPacket checks isOnline() and then calls getClientConnection() again (TOCTOU, :74-77).
  - C++: Connections are shared_ptr already (CONVENTIONS). Player→connection should be a shared_ptr snapshot (atomic<shared_ptr> or guarded) read once in sendPacket. Connection→Player must be weak or a handle (decision A), or the cycle must be broken explicitly in leaveWorld, as Java does. The alive-check timer must be cancelled in onDisconnect and must not keep the connection alive forever.
- **Client packets are thin and state-gated. Porting them means porting services, not network code.**
  - Evidence: readImpl totals 1,145 lines, with 114/190 at ≤3 lines. runImpl totals 3,011 lines, 126/190 at ≤15 lines, and mostly calls services (PlayerService, LegionService, BrokerService, ExchangeService...). AionClientPacket.run() re-checks isValid() before runImpl (:36-43) after the factory already checked the state (:294). 167/186 packets are IN_GAME-only.
  - C++: Client factory: a constexpr table of `{factory fn, EnumSet<State>}` indexed by opcode, replacing reflection. Port the ~20 CONNECTED/AUTHED packets (version check, auth, MAC, character list/create/delete/restore, passkey, enter world) first, as the login and character-select slice. Port the IN_GAME packets together with their services.
- **SM_SYSTEM_MESSAGE is half the network package and fully mechanical.**
  - Evidence: 28,958 lines; 4,119 `public static SM_SYSTEM_MESSAGE STR_*(...) { return new SM_SYSTEM_MESSAGE(id, args...); }`. Parameter types: String 3,090, int 444, long 33, byte 13, float 3, Player 3. There are 1,557 STR_ call sites (1,130 distinct) in src+handlers, plus 34 direct `new SM_SYSTEM_MESSAGE(id, Object...)`. writeImpl calls `param.toString()` at write time (lazy), and the generic entry points take Object... (PacketSendUtility.sendMessage/broadcastMessage/sendMonologue).
  - C++: Generate the C++ factories with a script from the Java file (name, id, parameter list) into a header of inline functions. Params become std::vector<std::string>, formatted at construction (int → decimal, Java-compatible float/long formatting). A variadic template can replace Object... at call sites.
- **Login and chat server links: outbound connections with fixed reconnect delays; their packets run unordered on the general thread pool.**
  - Evidence: LoginServer.connect: blocking SocketChannel.open. On failure it retries after 10 s (SocketException) or 60 s (LoginServer.java connect()). LoginServerConnection.onDisconnect → reconnect(): delay 5 s if it was AUTHED, else 15 s; disconnect() closes all pending login-request client connections. onServerClose → disconnect(). processData → ThreadPoolManager.execute(pck) (LoginServerConnection.java:80, ChatServerConnection.java:72), not a per-connection PacketProcessor. The first packet is SM_GS_AUTH / SM_CS_AUTH in initialized(). Buffers: LS 65,536, CS 16,384. The login flow is CM_L2AUTH_LOGIN_CHECK → registerLoginRequest, CM_MAC_ADDRESS → authenticateClient → SM_ACCOUNT_AUTH to LS → CM_ACCOUNT_AUTH_RESPONSE → AUTHED + SM_L2AUTH_LOGIN_CHECK. Reconnect: CM_RECONNECT_AUTH → SM_ACCOUNT_RECONNECT_KEY → client.close(SM_RECONNECT_KEY). SM_ACCOUNT_LIST holds List<AionConnection> read lazily; SM_LS_CONTROL/SM_CS_PLAYER_AUTH snapshot in the constructor.
  - C++: Use the documented commons pattern (`nioServer.openSocket` + registerConnection) and schedule reconnects on the game server scheduler; openSocket may block, so keep it off IO threads. The C++ login server already implements the other side (cpp/login-server/.../network/gameserver, GameServerFlowTest.cpp), which enables an early end-to-end test. Use a PacketProcessor per LS/CS connection for ordering, as the C++ login server did for GS packets (DEVIATIONS.md:137). Snapshot account ids in SM_ACCOUNT_LIST's constructor. The chat server link can only be tested once phase 3 (chat server) is ported.
- **AionConnection.writeData runs with the connection guard held and can recursively send packets. The C++ commons design already supports this.**
  - Evidence: AionConnection.java:204-220: synchronized(guard). It calls sendPacketInfo (for membership==10 it queues an SM_MESSAGE with the packet name during the write, :227-230) and records RunnableStatsManager stats per packet class. The C++ AConnectionBase guard is a recursive_mutex and writeData runs with it held (AConnection.h).
  - C++: Keep a recursive guard. With eager serialization, move the debug echo and the 8,192-byte warning to serialization time, and never serialize while holding the guard of a different connection.
- **Packet body splitting to fit the 8,192-byte client limit is computed when the packet is created, but the bytes are written later.**
  - Evidence: PlayerEnterWorldService.java:228-230 (DynamicServerPacketBodySplitList + SkillEntryWriter.DYNAMIC_BODY_PART_SIZE_CALCULATOR), :465-467 (FixedElementCountSplitList, 10 items per SM_INVENTORY_INFO), :490-492 (macros). SM_MAIL_SERVICE.java:23 and SM_HOUSE_SCRIPTS.java:18 use byteLengthForString (UTF-16 length). SM_INVENTORY_INFO's constructor modifies the caller's list (`items.removeAll(null)`, :26).
  - C++: byteLengthForString must use StringUtils::utf16Length. Eager serialization removes the gap between computing the size and writing. Keep the 32,768-byte write buffer: overflowing the C++ buffer disconnects, while Java only warns above 8,192.

## Risks
- 1. (Highest) Keeping Java's lazy write model in C++: cross-thread reads of mutable containers and strings (Effect lists, item blobs, names, legion data) from IO threads while game threads (PacketProcessor x4, ThreadPoolManager, AI) change them. That is undefined behaviour and crashes that are hard to reproduce. It also forces packets to extend game-object lifetimes, which pushes decision A toward shared_ptr everywhere. Changing to eager serialization is a deliberate deviation. The main behavioural difference is the timing of the 6 packets that change state in writeImpl, plus the moment state is sampled (send time instead of write time).
- 2. Byte-exact output of about 120 non-trivial server packets (SM_PLAYER_INFO 192-line writeImpl, SM_STATS_INFO, SM_CASTSPELL_RESULT nested effects, SM_PET 341 lines with switch-heavy subtypes, item info blobs with a recursive size computation) without a runnable Java reference. Mistakes show up as client crashes or silent UI corruption. Mitigation: golden byte tests derived by hand from the Java code, plus the real 4.8 client.
- 3. Per-recipient packets inside broadcasts (25 classes, including the very frequent SM_MESSAGE, SM_PLAYER_INFO and SM_DIALOG_WINDOW). A 'serialize once' optimisation that ignores the connection-dependent flag would send wrong race obfuscation or wrong enemy flags.
- 4. Cycles and lifetime between Player and AionConnection (10 s delayed leave-world, alive-checker task, LoginServer request maps), plus the sendPacket TOCTOU on player.getClientConnection(). Leaks with shared_ptr cycles, or use-after-free with raw pointers.
- 5. The crypt state machine edge cases: SM_KEY must be the first packet written and turns encryption on at write time; input is dropped before that; 3-strike decrypt failure; key advancing with unsigned 64-bit wrap. An off-by-one breaks the whole session, but this is easy to unit test.
- 6. SM_SYSTEM_MESSAGE generation: 4,119 factories with Object... params converted by toString(). Float, long and byte formatting must match Java's toString in the few non-String/int cases, and 160 handler broadcastMessage calls pass variadic Object params.
- 7. LS/CS packets run unordered on the general pool in Java. A C++ port that orders them (recommended) is a behaviour change. A port that keeps the pool must make LoginServer's maps and the account/state updates thread-safe.
- 8. PFF mode semantics contradict the config documentation (mode 1 disconnects in code). Choosing either way silently changes production behaviour for anyone reusing the config files.
- 9. Blocking connect in LoginServer/ChatServer.connect, and database work reached from packet paths. These must stay off Asio IO threads, as the C++ login server already does (DEVIATIONS.md:146).

## Dependencies
Depends on (already available in C++): commons network (AConnection/NioServer/PacketProcessor/BaseClientPacket/BaseServerPacket with buffer-passing writes), ByteBuffer (LE), StringUtils (UTF-16 lengths), configuration (NetworkConfig, PffConfig via bindPattern), Rnd, logging, RunnableStatsManager. The login-server C++ port already implements the LS side of the GS↔LS protocol (cpp/login-server/src/aion/loginserver/network/gameserver, tests/server/GameServerFlowTest.cpp).

Still needed from the game server before the network layer can be complete: ThreadPoolManager/scheduler (alive checker, reconnect, delayed broadcasts), the game object model (decision A: Player, Creature, Npc, Summon, Pet, Item, Effect, Legion, teams, houses), static data templates (decision B: packets read ItemTemplate, NpcTemplate, SkillTemplate, PetTemplate via DataManager in 6 writeImpls and all item blobs), KnownList/World (broadcasts), Account/PlayerAccountData + DAOs (character list), services (EventService, SiegeService, TownService, HousingService, ConquerorAndProtectorService, LegionService, AtreianPassportService, GameServer counters) used at write time by 16 packets, and the chat server (phase 3) for the CS link.

Things that depend on the network layer: every service and handler sends packets (PacketSendUtility: 2,400 sendPacket and about 800 broadcast/message calls across src and handlers; 6,168 `new SM_*`), the quest engine, AI (broadcastPacketAndAIEvent, broadcastMessage), instance handlers (SM_INSTANCE_SCORE writers), and admin commands (//fsc, //send use SM_CUSTOM_PACKET).

Suggested porting order within networking:

## Open questions
- Eager serialization (recommended) or keep lazy writes? If lazy, what replaces the JVM's tolerance for races: 1 IO thread plus game-state snapshots, or all game logic on a single strand?
- Should the 6 packets that change state in writeImpl (setLastCounterSkill, pet mood/gift cooldowns, WATCHING_CUTSCENE custom state, group/alliance event) move their side effects to the constructor or send path? Needs confirmation that send-time is acceptable, especially for the counter-skill timing comment in SM_ATTACK/SM_CASTSPELL_RESULT.
- PFF mode: port the code behaviour (mode 1 disconnects) or the documented behaviour (mode 2 disconnects)? Should the stale 0x0C4 example in pff.properties be corrected?
- Should LS/CS incoming packets be serialized per connection (a PacketProcessor per link) instead of Java's unordered ThreadPoolManager.execute? The C++ login server chose ordering for the reverse direction.
- Not verified: whether any handler (data/handlers) constructs packets on one thread and relies on them being written with later state. The heuristic grep found no handler-defined packet classes and only 2 fields caching packets (ArtifactAI.java:207-208), plus static constants in SM_FRIEND_RESPONSE/SM_MACRO_RESULT.
- Not verified: the byte-level correctness of the category counts (lazy 63 / connection-dependent 25 / global 10 / value 140). They come from a regex/brace-matching script over writeImpl and private write* helpers. Packets that call object getters through non-field locals or helper classes (ItemInfoBlob, InstanceScoreWriter, SkillEntryWriter) are partly undercounted.
- Not verified: whether Java's ByteBuffer order for the game connection is little endian in every path (assumed from commons AConnection; not re-read here), and whether the client ever sends trailing padding that the 'not fully read' warning would expose.
- How should `Object... params` be typed in C++ for SM_SYSTEM_MESSAGE / PacketSendUtility.sendMessage / broadcastMessage: std::string only with conversions at call sites, or a variant with Java toString formatting?
- Does the unmodified 4.8 client tolerate the C++ commons deviation 'consecutive packets batched into one write' (DEVIATIONS.md:96) on the game connection, as it did for the login server? The frames are identical, but this was only verified on the login server.

**Open for the owner (from the same night):**
1. **The play profile.** `gameserver.simple.secondclass.enable = true` (M5e D1 a) keeps 1006 / 2008 / 1007 / 2009 unregistered, as in Java. To play the retail route it must be false, and the game server restarted (the handlers read it at startup); the simple window then disappears for everyone. A starting-class character already at level 9 never gets 1006 / 2008 (the quest starts on a level change): ascend it through the window first, or set its `players.old_level` to 8 with the client closed. Characters that ascended through the window are not offered 1006 / 2008 again; they get 1007 / 2009 at their next level change.
2. **The four first-login handlers** `_1000Prologue`, `_1100KaliosCall`, `_2000Prologue`, `_2100OrderoftheCaptain` are held back: Java starts their quests at a character's first login, which changes what gs.scenario.m5a, m5b and m5b2 see, and U1/U7 does not let a phase-6 lane edit a phase-5 gate. Without them the missions 1001-1005 / 2001-2007 never start (1006 / 2008 do not need them). Recommendation: land them and let those three gates expect the Java-faithful prologue traffic (or seed their characters with 1000 / 2000 complete).
3. **A Java bug on the route:** QuestService.finishQuest pays 1006 / 2008's 73,200 exp before the completion event makes the character a Daeva, so at the level-9 cap the exp is lost; level 10 comes from 1007 / 2009's 13,125 exp (kept and marked `// java-bug kept`). Keep it, or fix it as a recorded deviation (the D7 precedent)?
4. `AbyssPointsService::addAp` is still unported: each raider or boss kill in the ascension instances logs an `onDie()` ERROR, and gives no AP and no loot (the quest still counts). It needs SiegeService and changes a phase-5 test; it stays with its milestone unless the owner wants it earlier.

## 1. Summary

The code the user's sessions and the gates run most (world and visibility, the object model, the controllers, the stats and combat
arithmetic, the every-session packets, persistence, the AI core and the startup/login/logout services) is **faithful to Java statement by
statement** almost everywhere. The auditors ran mechanical comparisons: all 160 `WorldMapType` constants, all 237 server opcodes, all 186
client packet table entries, all 4115 generated `SM_SYSTEM_MESSAGE` factories, 591 packet field types, the write-call sequence of every
`writeImpl`, the SQL text of all 56 DAOs and the order of their binds and reads. These found no divergence outside the items below.

What survived verification is **23 distinct findings**: **1 high, 6 medium, 16 low**. Most of them are not arithmetic slips. They are
`AION_UNPORTED` stubs or stale stand-ins that sit **inside ported code paths** and throw into a `catch` that hides them, or throw halfway
through a sequence Java completes.

- **The one high finding will hit the next client session.** The quest list never loads (H-1), so no advanced-class character is a Daeva. The
  M5c real-client checklist step 11 seeds exactly that character (GLADIATOR, quest 1006 COMPLETE, exp 126,069). It loads at level 9, not 10,
  and a higher Daeva is clamped to level 9 by its first exp gain, which the periodic save then writes to `players.exp`. **Fixing it needs
  more than the one-line stub.** Enter world would otherwise start throwing for every character with a quest row (§3.1, fix note).
- **One medium finding is memory safety on a hot path.** The NPC "most hated" sort re-reads live hate inside the comparator (M-1). Under a
  concurrent hate change, MSVC's unguarded insertion sort can walk before `begin()`: a crash in an unchecked build, a stalled NPC in the
  checked build.
- **Five medium findings need a database that came from the Java server:** a dead character bound on another map cannot log out or
  bind-revive (M-2); a character saved on one of 17 `except_buff` maps throws on every login (M-3); pets block login or vanish (M-4, M-5);
  friends vanish (M-6). A fresh C++ database does not reach them today.
- **Most of the 16 low findings are latent.** They are traps that go live when a neighbouring feature is ported: groups, quests, instances,
  pets, the remaining effects. One of them (L-6) goes live **when M5b-2 part 3 commits**, and so do the §6 watch items W-1 and W-2.

## 2. Scope and method

### 2.1 Why

The user plays the server with a real 4.8 client at the end of every milestone. So far those sessions found bugs no test had: a leaked
Player, an error on every kill, SiegeShield spawns, a missing target packet. This audit reads the code those sessions and the gates run
most, looking for **silent** divergences from Java before the next session finds them: wrong statement order, a dropped statement or branch,
an inverted or off-by-one comparison, a changed short-circuit, int wrap or float-cast differences, a different null path, missing atomicity,
a packet field with the wrong width, order or encoding, a persistence field not saved or loaded, a lifetime problem, a task not cancelled.

### 2.3 Method

- **Specification.** Java is the specification. The conventions in `docs/CONVENTIONS.md` and `docs/design/conventions-game-server.md`
  (int wrap, float casts, null, `synchronized`, collections, lifetimes) and the recorded deviations in `docs/DEVIATIONS.md` and
  `docs/deviations/<chunk>.md` were checked before anything was reported. A difference that follows a convention or a recorded deviation is
  not a finding.
- **Two passes.** An auditor read each area statement by statement, most-executed code first. A verifier then re-read every cited statement
  in both trees, checked reachability at HEAD, corrected citations and severities, and looked for missed divergences. A verifier's verdict is
  one of confirmed, downgraded (real, lower severity) or refuted.
- **Committed code only.** Other agents are editing the tree (M5b-2 part 3). Every C++ file with uncommitted changes was audited through
  `git show HEAD:<path>`. §2.5 lists those files.
- **Mechanical checks** (scripts under the scratchpad, §9): `WorldMapType` (160 constants, 0 differences); server opcodes (237) and the client
  packet table (186 entries, class and states); the write-call sequence of every `writeImpl` in serverpackets, iteminfo and skillinfo (only
  byte-identical structural splits and unported bodies differ); the 128 write calls of SM_PLAYER_INFO; 591 packet field primitive types; the
  read sequences of every ported CM packet; all 4115 generated SM_SYSTEM_MESSAGE factories (id, parameter count and order); PER_RECIPIENT
  declarations; the SQL text of all 56 DAOs with their bind and read order; the 53 PlayerAppearance get/set pairs and 54 DAO binds; 16 enum
  tables used on the wire.
- **Out of scope.** Code that is `AION_UNPORTED` or `AION_PARTIAL` by design and reachable only through another unported entry point is
  not a divergence. It is reported only when it sits inside a ported path that runs, or when its ordering turns a missing feature into
  wrong behaviour (for example L-9).

### 2.4 Severity scale

| Severity | Meaning |
|---|---|
| high | Wrong behaviour that a player or the persistence can hit |
| medium | Reachable but rare, or cosmetic on the wire |
| low | Latent: no path reaches it at HEAD, or no difference is observable in the shipped (MSVC) build |

Reachable-but-rare includes "needs a database that was carried over from the Java server". The C++ server uses the same `aion_gs` schema
(`cpp/README.md`), so this is a supported setup, but the user's own sessions create new characters (`m5b-client-session.md`).

#### P5-06 quest data model (caller in P4-14)

#### H-1 · The quest list load throws on the first `player_quests` row, so no advanced-class character is a Daeva: level-9 cap and permanent exp loss

- **Severity:** high (confirmed). **Found by:** persistence auditor; confirmed by the persistence verifier.
- **Java:** `dao/PlayerQuestListDAO.java:50`; `model/gameobjects/player/PlayerCommonData.java:276-281` (in `setExp`) and `:595-609` (`updateDaeva`)
- **C++:** `dao/PlayerQuestListDAO.cpp:70`, which calls `questEngine/model/QuestState.cpp:73-75` (`AION_UNPORTED`). The throw lands in the
  DAO's `catch (const std::exception&)` at `:73-75`. The Daeva logic is `model/gameobjects/player/PlayerCommonData.cpp:190-196, 272-285`.

```java
questState.setPersistentState(PersistentState.UPDATED);
int maxLevel = isDaeva || !online && (updateDaeva() || exp > pxt.getStartExpForLevel(10)) ? pxt.getMaxLevel() : 10;
// updateDaeva: if (elyAscentQuestStatus != QuestStatus.COMPLETE && asmoAscentQuestStatus != QuestStatus.COMPLETE) return false; setDaeva(true);
```
```cpp
questState->setPersistentState(Persistable::PersistentState::UPDATED);
void QuestState::setPersistentState(PersistentState value) { AION_UNPORTED(); }
```

**Consequence in play.** The first `player_quests` row throws inside the DAO's catch-all. The DAO logs "Could not restore QuestStateList" and
returns an empty list, so the quest journal and the completed-quest list are empty. `PlayerDAO::loadPlayerCommonData` (`PlayerDAO.cpp:170-171`)
calls `setPlayerClass` and then `setExp` while `online` is still false. That runs `updateDaeva()` on the empty list, so `isDaeva` stays
false for every advanced-class character whose ascension quest (1006 or 2008) is COMPLETE.
- (a) A character with exp exactly `getStartExpForLevel(10)` = 126,069 loads at **level 9** in C++ and level 10 in Java. That is exactly the
  seed in the M5c real-client checklist, step 11 (`m5c-plan.md:823-831`: GLADIATOR, a `(1006, COMPLETE)` row, exp 126069, "Log in: you are
  a level-10 Gladiator"). It is also the M5c gate seed D5 (`m5c-plan.md:691`). So crafting check C19 fails silently.
- (b) A higher Daeva (for example a level-30 Gladiator from a Java-era database) loads at the right level. Its **first exp gain** then
  calls `setExp` with `isDaeva` false and `online` true. The exp gain path is live: `NpcController.cpp:267` `addExp`. The call clamps exp to
  126,069 and the level to 9 (`onLevelChange(30, 9)`). `GeneralUpdateTask` (every 900 s) or the logout save then writes the clamped
  `players.exp`: **every level above 9 is lost for good**. The quest rows themselves are not touched. Death does not clamp, because
  `calculateExpLoss` sets exp directly.

**Verification.** The verifier re-read every link at HEAD. None of the files has uncommitted changes. `setExp`/`updateDaeva` match Java
statement for statement, so the empty list is the only difference. No `DEVIATIONS.md` row covers it. `m5d-plan.md:333` (untracked) records
the unported `setPersistentState` only as an empty list, not the Daeva or exp consequence. The test that would catch it hides it:
`tests/dao/PlayerDaoTest.cpp:624` skips on `setPersistentState` with `SKIP_IF_UNPORTED`. Correction to the auditor: the current step-11 SQL
*does* include GLADIATOR and the 1006 row.

**Proposed test.** `PlayerDaoTest`: insert a `players` row (`player_class 'GLADIATOR'`, exp 126069) and a `player_quests` row
`(id, 1006, 'COMPLETE')`. Call `PlayerDAO::loadPlayerCommonData(id)` and expect `getLevel() == 10` and `isDaeva()`. Second case: exp =
`getStartExpForLevel(30)`, then `setOnline(true)` and `setExp(exp + 1)`; expect the level to stay 30. Change
`PlayerDaoTest.QuestStateListLoadAndStore` so that `SKIP_IF_UNPORTED` on `setPersistentState` fails the test. Add an enter-world scenario for
a character with a COMPLETE quest row: it must reach in-world and send `SM_QUEST_COMPLETED_LIST` with the quest.

**Fix note (checked by the report writer at HEAD).** Porting `setPersistentState` alone would make things worse. `SM_QUEST_LIST.cpp:24` calls
`QuestVars::getQuestVars()`, and `SM_QUEST_COMPLETED_LIST.cpp:29` calls `QuestState::canRepeat()`. Both are `AION_UNPORTED` at HEAD, and the
network audit lists "characters with any quest" among those that cannot log in. Today the empty list hides both. Once the list loads, enter
world would throw at `PlayerEnterWorldService.cpp:460-461` for every character with a quest row, including the step-11 seed. So the lane
must port `setPersistentState`, `canRepeat` and `getQuestVars` together, and preferably the whole pure-data set that `m5d-plan.md` §3.6 tracks.
A grep counts 13 `AION_UNPORTED` bodies in `QuestState.cpp` and 3 in `QuestVars.cpp`, all small (Java `QuestState.java`, `QuestVars.java`).
The same lane closes L-1. **Until it lands, do not run the M5c step-11 seed and do not log in a Java-era Daeva.** The character loses its
levels on the first kill.

### 3.2 Medium

#### P5-01 stats (waits for M5b-2 part 3)

<a id="m-1"></a>
#### M-1 · `AggroList` MOST/SECOND/THIRD_MOST_HATED sorts with a comparator that re-reads live hate; MSVC's unguarded insertion sort can run before `begin()`

- **Severity:** medium (confirmed). **Found by:** AI auditor; confirmed by the AI verifier.
- **Java:** `controllers/attack/AggroList.java:168-170`
- **C++:** `controllers/attack/AggroList.cpp:57-66` (`nthMostHated`), used at `:227-232`. It is reached from `ai/manager/SimpleAttackManager.cpp:114`,
  `ai/manager/AttackManager.cpp:93`, `handlers/.../ai/GeneralNpcAI.cpp:101` and `ai/AbstractAI.cpp:147`. The file is unchanged in the working tree.

```java
case MOST_HATED -> stream.max(Comparator.comparingInt(AggroInfo::getHate)).map(AggroInfo::getAttacker).orElse(null);
case SECOND_MOST_HATED -> stream.sorted(Comparator.comparingInt(AggroInfo::getHate).reversed()).limit(2)...
```
```cpp
std::stable_sort(sorted.begin(), sorted.end(),
    [](const Ptr<AggroInfo>& a, const Ptr<AggroInfo>& b) { return a->getHate() > b->getHate(); });
```

**Consequence in play.** `AggroInfo.hate` is a `runtime::Field<int32_t>` (`AggroInfo.h:27`). Each read is a fresh atomic acquire load
(`Field.h:42-44, 157`). Other threads change it without a common lock while the sort runs: `addHate` from player hits on packet threads,
`AggroNotifier` on the pool, and the 10 s hate-reduction task. `P5-01.md:20` keeps this as a Java race. For up to 32 elements
(`_ISORT_MAX`, `<algorithm>:566`), MSVC 14.51 `stable_sort` uses `_Insertion_sort_unchecked` (`<algorithm>:8915-8937`). That function tests
`pred(_Val, *_First)` once. Its inner loop `for (_Prev = _Hole; pred(_Val, *--_Prev); ...)` has no lower bound. If the order of two attackers
flips between the two reads, `_Prev` steps to `begin() - 1`. Two party members with equal hate, one landing a hit between two comparisons,
are enough. The sort runs on every NPC swing (`attackAction`) and every chase tick (`targetTooFar`) whenever two or more attackers have hate.
- In an unchecked Release build, the sort reads heap memory before the vector as a `Ptr<AggroInfo>`: an access violation that takes down the
  server, or an out-of-bounds write.
- In the checked build the dev server runs (`Ptr` = `{T* p, uint64 stamp}`, `Ref.h:170-172`), `checkDereference` (`Ref.h:50-57`) most likely
  rejects the stray element and throws `NullPointerException` or the stale-borrow `IllegalStateException`. That aborts `getTarget` inside
  `SimpleAttackManager::attackAction` before ATTACK_COMPLETE, so the NPC stays in FIGHT with no swing scheduled until another event re-arms it.

Java is memory-safe here: MOST_HATED is a linear `max()`, and `sorted()` uses TimSort's bounded `binarySort` below 32 elements.
`P5-01.md:48` argues only that the single-threaded result is the same element, so no deviation covers concurrent writers.

**Verification.** Every link was re-read: `Field` semantics, the lack of a lock, and the MSVC library lines. The checked-build refinement
above is the verifier's. The race window is nanoseconds per call, so medium (reachable but rare) is right.

**Proposed test.** `tests/stats`: `AggroListConcurrencyTest.MostHatedSelectionIsMemorySafeUnderConcurrentHateChanges`, run under the
`msvc-asan` preset. An NPC with two known attackers of equal hate. Thread A loops `getTarget(MOST_HATED / SECOND / THIRD)` 10^6 times.
Thread B alternately calls `addHate(+1)` on each attacker and `reduceHate`. Expect no ASan report and always a non-null attacker. Add a PCT
variant (`tests/runtime/support/PctSupport.h`) that schedules a writer at the `Field::get` yield point between the two comparator reads.

**Fix note.** Snapshot each hate once into `std::vector<std::pair<int32_t, Ptr<AggroInfo>>>` and sort the snapshot. Use a linear first-max for
MOST_HATED. `AggroList.cpp` is not among part 3's modified files, but P5-01 is part 3's chunk, so this waits for wave 2 (§8), unless the user
prefers part 3's lane to take it into its commit.

```java
    ConquerorAndProtectorService.getInstance().onLeaveMap(player);
```


**Consequence in play.** This affects any character whose `player_bind_point` row is on a different map from the one it dies on. The typical
case is a character from a Java-run database, bound in Sanctum or Pandaemonium, that dies in Verteron or Altgard.
1. **Logout while dead** (CM_QUIT, the delayed `leaveWorld` after a disconnect, or `safeLogout` at shutdown). `revive()` runs and
   `World::despawn` removes the player from view. Then `UnportedException` leaves `leaveWorld`, so nothing after it runs: storing effects,
   item cooldowns and life stats, the group logout, `removeAllEffects`, `controller().delete_()`, `storePlayer` and
   `PlayerDAO::onlinePlayer(false)`. CM_QUIT never sends `SM_QUIT_RESPONSE`, so **the client hangs**. On the disconnect path the Player stays
   registered in World, invisible, and `players.online` stays 1. Every re-login then gets REENTRY_TIME until a restart runs
   `setAllPlayersOffline`. If a second `leaveWorld` runs later (CM_QUIT, then the client is killed), the player is alive by then, so that
   logout completes. But it saves the death position instead of the bind point Java would store.
2. **CM_REVIVE bind revive.** The player is revived and despawned, but `SM_CHANNEL_INFO` and `SM_PLAYER_SPAWN` are never sent. The character is
   **stuck invisible** until it relogs.

Characters created in C++ are not affected at HEAD. They have no bind point (only ResurrectAI sets one, and that is O-08), and they cannot
leave their start map, so `moveToBindLocation` stays on the same map, whose arm is ported. The committed deviations do not record this. Only
the uncommitted `P5-03.md` and the untracked `capacity-proposals.md` §4.3 mention the cross-map arm, and only for ReturnEffect. Inferred by the
report writer, not separately verified: the L-2 correction applies here too. Because `delete_()` is skipped, the periodic PLAYER_UPDATE and
INVENTORY_UPDATE tasks keep saving the players row (at the death position) while the Player stays in World.

**Proposed test.** `PlayerLeaveWorldServiceTest.ADeadPlayerWithABindPointOnAnotherMapIsRevivedThereAndSaved`: spawn a player on 210010000
with `setBindPoint(BindPointPosition::create(110010000, x, y, z, h))`, kill it, and call `PlayerLeaveWorldService::leaveWorld`. Expect no
exception, `World::isInWorld(objectId)` false, `PlayerDAO::isOnline` false, and the pcd map/x/y/z equal to the bind point. Companion:
`PlayerReviveServiceTest.BindReviveToAnotherMapSendsChannelInfoAndPlayerSpawn`. Both fail today with `UnportedException("onLeaveInstance")`.

**Fix note (checked by the report writer).** Java `InstanceService.onLeaveInstance` (`InstanceService.java:210-224`) calls the instance

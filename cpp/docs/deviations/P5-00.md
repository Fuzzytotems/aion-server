## Correction 2026-10-03: a landed glider's flight time (owner's bug report; `C++` branch only, not `4.8`)

A correction of the Java code, approved by the owner for the `C++` branch only. **The bug (Java's too):** glide, click a spot on the ground,
land - the flight time kept burning while the character walked on to the spot. `CM_MOVE` (CM_MOVE.java:151, 188-201) ends a glide only on a
FALL packet or an IMMEDIATE (arrived) one; the walk to the clicked spot is POSITION|MANUAL|ABSOLUTE packets (0xE0) without GLIDE, so the
server kept the player in GLIDING and LifeStatsRestoreService's FP reduce task running until he arrived. **The correction**
(`CM_MOVE.cpp`, the non-FALL branch of runImpl): a new move command (POSITION|MANUAL) without the GLIDE flag from a gliding player calls
`FlyController::onStopGliding` (FP restore, or the flying rate if he also flies; STOP_GLIDE). Every packet sent while gliding carries GLIDE (its
glide flag byte follows), and a packet that is no new move command (a continuation) keeps the glide, so a glide is not ended mid-air by it.
**Amended the same day after the owner's play test** (the first version required MANUAL and did not fire): the traced session (Fuzzytotem,
10:31-10:35) shows the click-to-move walk after landing is 160, POSITION|ABSOLUTE without MANUAL; in the air every position packet carried
GLIDE (196, 132, 228, 164) and no glide-less position packet came between them. The condition is now a position packet without GLIDE.
It is logged (`Glide of <name> ended by a move without the glide flag (type=<n>)`), so a play session can confirm it fires only on landing.
**Test:** `SocialAndFlightPacketsTest.ALandedGliderWhoWalksOnToAClickedSpotStopsGliding` (fails without the correction).

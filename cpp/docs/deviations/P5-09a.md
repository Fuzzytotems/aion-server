# P5-09a drop, rewards and packs: deviations

P5-09 was split into P5-09a (drop, rewards, passport, bonus and faction packs, guide), P5-09b (trade and market) and P5-09c (mail and craft) for
M5c (m5c-plan.md D1, I-01). The rows of the shared `P5-09.md` from waves 5a to M5b-3 stay there (among them M5b-3's drop services); this file
holds P5-09a's rows from M5c on.

## M5c stage 1 (mail lane, m5c-plan.md R-02)

Ported: `StarterKitService.onLevelUp` (StarterKitService.java:63-75), the file's only `AION_UNPORTED`. It is reached only with
`gameserver.custom.starter_kit.enable` (default false, `PlayerController::onLevelChange`). Tests: `tests/economy/P5-09a/StarterKitServiceTest.cpp`
(on the mail lane's `tests/economy/P5-09c/MailTestSupport.h`, found through the executable's include directories; five verbatim item rows of
the level-1 and level-25 kits). Mutation-proven with the mail lane's schemata build: both loop bounds, the missing-level guard, the letter type
and the item count, each mutant killed.

| Area | Java | C++ | Reason |
|---|---|---|---|
| The level loop | `for (int level = fromLevel; level <= toLevel; level++)`: with `toLevel == Integer.MAX_VALUE` the `int` wraps and the loop never ends | the same `int32_t` loop; its increment past `INT32_MAX` would be undefined | The only caller passes character levels (`minNewLevel`, `newLevel`), so neither tree reaches it |

## Ascension lane (2026-09-28 night lanes, on the M5d engine overlay)

Ported: `WebRewardService::MaxLevelReward::isPendingAscension` (WebRewardService.java:102-104, `pendingAscension.contains(objectId)`), the one
body of the class the retail ascension route calls: `_1006Ascension` / `_2008Ascension.onQuestCompletedEvent` ask it right after
`updateDaeva` (_1006Ascension.java:278-285, _2008Ascension.java:298-305), inside the single try of `QuestEngine::onQuestCompleted`
(QuestEngine.cpp:260-271), where the unported body would have logged an ERROR at every ascension and skipped the handlers after it. The rest
of the class (`reward`, `addBasicGear`, `sendAvailableRewards` and its two helpers, the web "level 65" reward) stays `AION_UNPORTED`; it is the
only writer of the set, so on this port the answer is false for everybody until it lands. **No deviation.** Test:
`tests/economy/P5-09a/WebRewardServiceTest.cpp` (empty set, the object id added as `reward` adds it, another character, the id removed as
`reward`'s Daeva arm removes it). Mutation-proven with a schemata build (the variable `AION_ASC_MUT`, the original restored after the build
and checked by sha256): the answer inverted, always false, always true, "any id pending"; each mutant killed.

## M5d stage 1 (dialog-and-rewards lane, m5d-plan.md E-09; the lane's file lease on `services/reward/BonusService.*`)

Ported: `BonusService` whole (BonusService.java:27-81): `getQuestBonus`, `getMatchingItemsOfRandomGroup` and `getBonusGroups`.
`QuestService::getRewardItems` asks `getQuestBonus` for every quest with a `<bonus>` (760 XML quests, the 574 work orders among them,
m5d-plan.md §18.2). `getQuestBonus` already had the value-typed return of `m5d-h01` (D17 b). Tests: `tests/economy/P5-09a/BonusServiceTest.cpp`
(10 cases, the shipped rows of 13 quests, the complete medal group and documented cuts of the craft, manastone, food, medicine and event
groups: one quest of each implemented type). `getBonusGroups`' NONE arm is not driven: `<bonus>`'s type is a required attribute, no quest
of the data names NONE, and the function is private.

| Area | Java | C++ | Reason |
|---|---|---|---|
| `getMatchingItemsOfRandomGroup` when no group is drawn | `null` when no group could be drawn at all (no group of the type, or chances summing to 0), else the last filtered list, which may be empty | an empty vector in both cases | The frozen header returns `std::vector` by value, which has no null. The only caller, `getQuestBonus`, answers no item for both: Java's null check, and `Chance.selectElement` over an empty list returns null. So no caller can tell them apart |

The unimplemented types (every type but EVENTS, FOOD, MANASTONE, MEDICINE, MEDAL, TASK, MOVIE and NONE: BOSS, FORTRESS, MAGICAL, RIFT ... in
the data) log Java's warning "Bonus of type X is not implemented" under the Java logger name and give no bonus, as in Java.

**Mutation evidence.** One mutant-schemata build of the lane (the variable `AION_D1_MUT`; the nine touched production files were copied to
the session scratchpad first, restored right after the runs and checked against their recorded sha256, then rebuilt clean). Here 8 mutants,
all killed: no fall-through to the next group (B1: `AWorkOrderBonusFallsThroughTheCraftGroupsThatHaveNoMatch`,
`TheItemsFollowThePlayersRaceNotTheQuests`), `matches` ignored (B2: four cases), MEDAL answered with the craft groups (B3), no warning for an
unimplemented type (B4), a count of 1 instead of the entry's (B5), TASK answered with no group (B6), MOVIE warned about (B7), and an item
for a quest without `<bonus>` (B8: `AQuestWithoutABonusGetsNone`).

**Mutation evidence after the lane's review.** The review's surviving mutants were closed with new cases, and proved in a second
schemata build (the variable `AION_D1F_MUT`). The five production files of the fix (BonusService, AbyssPointsService, GloryPointsService,
QuestStartAction, ReadAction) were copied to the session scratchpad first. After the runs they were restored, checked with `sha256sum -c`,
and rebuilt clean. There were 17 mutants, and each was killed by the case written for it; with the variable unset, all cases pass. The four
here: EVENTS answered with the food groups (the review's 1: `AnEventsBonusIsARowOfTheEventGroupAtTheBonusLevel`), FOOD with no group (2:
`AFoodBonusIsTheLevelRowsOfThePlayersRace`), MANASTONE with the medicine groups (3: `AManastoneBonusIsTheLevelRowsOfTheCommonOrTheRareManastoneGroup`)
and MEDICINE with the manastone groups (4: `AMedicineBonusIsTheLevelRowsOfOneOfTheThreeMedicineGroups`). The review's 5 (NONE warned about)
stays unkillable by the data, as said above. P5-08.md and P5-07.md list the other 13.

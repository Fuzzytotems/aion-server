**Closed after the review (2026-09-24), outside this lane's files:** the row "`QuestEngine.init`, `drop.setQuestId(data.getId())` … the holder
sets it while loading" above described code that did not exist: nothing called `QuestDrop::setQuestId`, so every `<quest_drop>` of the static
data kept `questId` null and `isQuestDrop` threw Java's NullPointerException for it (Java unboxes `drop.getQuestId()`) — with `registerDrop`
ported, on every kill of an npc that has a quest drop (20 item ids on Poeta, e.g. 210668 *pinkbeak airon*), and `onDie`'s catch logged one
ERROR per kill. `QuestsData::afterUnmarshal` (P4-09) now sets it on every `<quest_drop>` of every quest before the holder is published — the
design `DEVIATIONS.md` "static data templates" row `QuestDrop.questId` describes (P4-07b.md is merged there) — and `QuestEngine::init` reads it
as its comment says. `QuestDropTest`'s fixture no longer sets the ids itself; `QuestDropTest.TheHolderGivesEveryQuestDropItsQuestIdAndInitRegistersItForTheKill`
binds the shipped rows through the holder, runs `QuestEngine::init` and kills 210668 with a character without quest 1108 (no drop, no
exception); removing the holder's assignment fails it and every case that reaches `isQuestDrop`.
`isQuestDrop`'s `ALLIANCE`-target and `MENTE` arms answer false for a solo player: `QuestDropTest.AnAllianceQuestDropsNothingForAPlayerOutsideAnAlliance`
(quest 30408), `AMenteeQuestDropsNothingForAPlayerOutsideAGroup` (quest 37001); the in-team halves need a group or an alliance (M5g).

**Closed by M5d stage 1a (E-01; the integrator's edit when the overlay was rebased onto `a75d281ff`, 2026-09-28, as P5-06a.md asks):** the
row "`isQuestDrop`, a drop with a collecting step … Throws" above. E-01 ported `QuestState::getQuestVarById` and `QuestVars::getVarById`, so
the collecting step is compared as Java compares it (QuestService.java:760-763), with no deviation left. The test that pinned the throw
became `QuestDropTest.ACollectingStepDropsOnlyWhileTheQuestsFirstVariableIsAtThatStep` (quest 1001's drop on 210671, collecting_step 7: no
drop at variable 0 = 0, 6 or 8, nor with variable 1 = 7; one Kerubar Fang at variable 0 = 7). From M5d on the engine's rows are in
`P5-06a.md`, the handler base's in `P5-06b.md` and the XML templates' in `P5-06c.md`.

## M5d stage 3, E-08 (2026-09-29; the rows the stage-3 task gave this lane)

**Closed by E-08:** the wave 5a row "`QuestEngine.init`, `gameserver.analysis.quest_handlers`" and the D3 join's row "The P5-06 acceptance
row (m5d-plan.md D8)" above. `QuestSpawnAnalyzer` is ported (P5-06a.md, "M5d stage 3, E-08", has its rows, tests and mutation proof), and
with `gameserver.analysis.quest_handlers` on `QuestEngine::init` hands `QuestSpawnAnalyzer::run` to the long-running pool
(QuestEngine.java:107-108). The `AION_PARTIAL` at `QuestEngine.cpp:115` is gone, and P5-06 has no `AION_PARTIAL` site left. The acceptance
row's analyzer column, "QuestSpawnAnalyzer output equals the Java-regex expectation on the ported set", is
`QuestSpawnAnalyzerRealDataTest.TheHandlerSpawnedNpcIdsAreJavasPatternOverThePortedHandlers` (`tests/quest/QuestSpawnAnalyzerTest.cpp`, P5-06a):
the npc ids the analyzer takes as spawned by handlers - the build-time table of `aion_gs_regscan`, which `aion_game_server` links - equal the
set `tools/parity/parity.py spawn-analyzer` finds with the analyzer's own regular expression over the ported handler sources (61 files, 6
ids on 2026-09-29). The test executable links the real npcids table for it (game-server/CMakeLists.txt). What the row closes is the
Java-regex part: the set of npc ids the handlers spawn, the one input of `run` that the port computes differently (at build time). The rest
of `run` is Java's statement by statement and its rules are pinned by `QuestSpawnAnalyzerTest`'s unit cases; its whole output over the real
data (119 lines on 2026-09-29) matched a throw-away re-derivation once (P5-06a.md), which is not a committed test. The seven allow-list rows
of the site are deleted (m5a, m5b, m5b2, m5b3, m5c, m5d and travel; the m5d row was in §B, the others in §C or, for m5a, in its only
section), the M5d gate checks instead that its server does not run the analysis (C17, m5d-plan.md §21.2), and every gate was run on the
result. `QuestEngineTest.InitRegistersEveryXmlQuestAndReachesOnlyTheSpawnAnalysisPartial`, named above, is
`InitRegistersEveryXmlQuestAndRunsTheSpawnAnalysisOnTheLongRunningPool` now.

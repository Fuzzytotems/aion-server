It can only drop a tick, and no reachable configuration produces one: the first tick comes one period after the constructor started, and a period of 0 or less throws in `scheduleAtFixedRate` exactly as `ScheduledThreadPoolExecutor` does in Java |

| Area | Java | C++ | Reason |
|---|---|---|---|
| `--log-folder=<dir>` | logback.xml sets the property `logFolder` to `log`; every server process of one directory shares it | C++-only command line option of `main.cpp` (default `./log`, so a normal start is unchanged): it replaces `Logging::Config::logFolder` before `Logging::init`, which also moves the check modes' default report directory to `<log>/m4`. `cmake/RunStartupSmoke.cmake` and `cmake/RunM4Check.cmake` give every server run its own directory, and the smoke test fails when `<OUTPUT_DIR>/log/server_console.log` is missing | `Logging::init` archives **and deletes** the `*.log` files it finds, so two server processes in one log directory make each other's archiving fail ("Error gathering and archiving old logs"). ## Wave 5a, stage 2 phase 4 (final fixer)

| Area | Java | C++ | Reason |
|---|---|---|---|
| `CheckOutput::runFinalCensus` and `census.txt` | – | After the pool drain, the final scan reclaims until no reported entry has refcount 0 any more (bounded by the same deadline) and drops any that remain | An entry with refcount 0 is **not** a leak. `LeakCensus` only ever reports an object that was still referenced when a census check ran (`if (count == 0) continue; // waiting for reclamation`), so a 0 in the final scan means the last reference went away after that check and the object is merely waiting for the reclaimer's sweep, which also removes its table entry. Measured under a full `ctest -j 6`: `census.txt` carried one `Player` with refcount 0 and no pinning task while `live_counts.txt` already reported 0 live Players and `censusLeaks` was 1 — a §5.7 Q8 failure with nothing leaked. The unloaded runs of the same tree had an empty census |
| `m5a_summary.txt` `knownListNotifyFailures` | `KnownList.notifySee/notifyNotSee/notifyNotKnow` swallow every exception and log it as `log.error("", ex)` — with an **empty** message | `CheckOutput::writeSummary` emits `knownListNotifyFailures <KnownList::notifyFailureCount()>` next to `unportedHits` and `partialHits`, and §5.7 Q8 asserts it is 0 | W-07 asks that "each `notify*` catch counts as a failure". The counter and its test were delivered by the fix-world lane (P4-10), but nothing read it: `writeSummary` had no such key and case 8 never looked for one, so the item was reported done at both ends and landed unwired. Without the line, a controller that throws on every notification shows up only as an unattributable ERROR line, which Q8 catches solely because Java logs at ERROR level at all |

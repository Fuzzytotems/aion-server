### Correction of the Java code (owner's decision 2026-10-05, both branches)

- **`PlayerTeamDistributionService.doReward`'s quest kills run outside the team lock.** Java calls `QuestEngine.onKill(new QuestEnv(owner,
  member, 0))` for every in-range online member inside `PlayerTeamRewardStats.accept`, which `team.forEach` runs under the team lock
  (PlayerTeamDistributionService.java:38-43, 118-123): every quest handler's `onKillEvent` runs under it, takes its own locks there (quest
  state, inventory, the npc) and may reach this or another team, an inversion of the order those paths take. The port's `accept` collects
  the member instead (`PlayerTeamRewardStats::questKillers`, a `Ref` each), and `doReward` calls `onKill` for them in the same order right
  after the `forEach` (or the league's alliance loop) released the lock, before the "nobody nearby" return, so the same members get the same
  kill. The same pattern as PR #77's `CondSkillLauncherEffect` lock-order correction. Test: `tests/team/P5-10a/TeamQuestKillOrderTest`
  (a quest probe takes a lock the test first takes outside the team lock; Java's order closes a `CYCLE`, verified by reverting to it).
  Logged in [owner-decisions.md](../design/owner-decisions.md) (2026-10-05).

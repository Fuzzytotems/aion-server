# Deviations of chunk P4-07b (templates: every model.templates subpackage not in P4-07a, item actions excluded)

To be merged into [../DEVIATIONS.md](../DEVIATIONS.md) by the integrator. The code marks each one with a `Deviation:` comment or a `C++:` note in the
class comment.

## game server / static data templates

| Area | Java | C++ | Reason |
|---|---|---|---|
| Exceptions of afterUnmarshal hooks | `SummonGroup`, `GlobalDropItem`, `ItemRaceEntry` and `StaticDoorWorld` throw `IllegalArgumentException`; `HouseAddress` throws `NullPointerException`/`ClassCastException` outside a `HousingLand`; `WalkerTemplate` throws `NumberFormatException` for malformed `rows` and `IndexOutOfBoundsException` without steps; `AssaultData` throws `NullPointerException` for an assaulter without `type` or `npc_ids`; JAXB aborts the load | `LoadContext::fail` throws `StaticDataException` with the Java message (the parse error text for `rows`) and the file/line/element location | The loader's error type; startup fails the same way (none of these occur in the data), as in P4-07a |
| `GlobalDropItem` and `ItemRaceEntry` item checks | `(staticData != null ? staticData.itemData : DataManager.ITEM_DATA).getItemTemplate(id)` | The item templates of the current load are found through their XmlIDs (`LoadContext::findXmlId<ItemTemplate>`), without the fallback to the published `ITEM_DATA` | Written before `ItemData::getItemTemplate` existed (header request templates-b-1 added it and kept the hooks: in a full load the XmlIDs are the same templates); item groups, global drop rules and events always load together with the items, and //reload is deferred (D3). Same rule as P4-07a's `ResultedItem` |
| `QuestDrop.questId` | `QuestEngine.init` calls `setQuestId(questId)` on the drops of the published quest templates | `QuestDrop::setQuestId` is a C++-only non-const setter for the holder (`QuestsData`, P4-09) to call while loading; `QuestEngine::init` only reads the id | Templates are const after publication; the value is the owning quest's id either way |
| Lazily created template lists | `CollectItems.getCollectItem`, `ExMaterials`/`Materials.getMaterial`, the `GlobalDrop*` list getters, `IGCategory.getSubCategories`, `InstanceBonusAttr.getPenaltyAttr`, `RouteParent.getRouteVersion`, `ShoutGroup.getShoutNpcs`, `ShoutList.getNpcShouts`/`getNpcIds`, `StreamLocations.getLocation`, `TradeListTemplate.getTradeTablist` and the `Tribe` relation getters create (or replace) the list on the first call, and `QuestKill.getNpcIds` moves `npc_ids` into a new list; unsynchronized writes to shared static data | The getters are const and return the bound list, or an empty list where Java stores a new one; no template is modified | D6: obvious race on shared static data (templates are const after load); the returned contents are Java's. Tests: `QuestTemplatesTest.ListsAndFlags` (repeated `getNpcIds`), `MiscWorldTemplatesTest.ShoutsPanelsRecipesRidesMaterials` |
| `TradeListTemplate.getCount` | `tradeTablist.size()`: `NullPointerException` for a template without `<tradelist>` whose `getTradeTablist()` was never called | 0 | Follows from the row above (the list always exists); every caller reads a template with lists |
| `Buff.afterUnmarshal` warning | Prints the `skill_ids` HashSet in its hash order | Prints the ids in ascending order | Log text only |
| `DoorRepairData.getRepairStones` | `HashMap.values()` order | Ascending static id order | Nothing calls it; the lookups (`getRepairStone`) are unchanged |
| Java overrides of frozen shells | `ItemRaceEntry.getCount`/`getChance`/`matchesQuest`/`matchesLevel` (overridden by the rewards classes), `BonusItemGroup.getItems` (abstract), `MailPart.getType`/`getParamValue` (overridden by `Sender`, `Title`, `Header`, `Body`, `Tail`) and `PlaceableHouseObject.getTypeId` (abstract) are virtual | New virtual functions would change the layout of frozen shells: the base functions select the concrete class through a C++-only private `entryClass`/`groupClass` tag (set only through the protected constructor each subclass calls) or the generated `javaClassName()` and call its non-virtual function of the same name; `BonusItemGroup::getItems()` returns `std::vector<const ItemRaceEntry*>`, the subclasses their typed lists | Same results through base and derived types (tests: `ItemGroupTemplatesTest.EntryClassesAndGroups`, `ItemGroupTemplatesTest.MatchesDispatchOnTheEntryClass`, `HousingTemplatesTest.PlaceableObjectsAndEnumCompanions`, `MailTemplatesTest.SystemMailsFormatting`); the shells do not list the Java interfaces `Chance` and `IMailFormatter` as bases, since `Chance::selectElement` is a template and custom mail formatters implement `IMailFormatter` |
| Custom mail formatters | `MailFormatter` passes anonymous `MailPart` subclasses overriding `getParamValue` | Custom formatters implement `mail::IMailFormatter`; `MailPart::getFormattedString(const IMailFormatter*)` and `MailTemplate::getFormatted*` take them (nullptr for Java null) | Static data parts cannot be subclassed at run time; the only method Java calls on a custom formatter is `getParamValue` |
| Template objects created at run time | `new HandlerSideDrop(...)` (stored in `QuestService.questDrop`), `new FlyRingTemplate(...)` (kept by `FlyRing`) are garbage collected | The classes keep Java's constructors; their callers (QuestEngine, instance handlers) allocate them once and never free them, like templates referenced as `const T*` | No GC; the objects are created at startup or per instance handler registration and are few |
| Index maps of templates | `HashMap`/`EnumMap` members filled by the hooks, bound lists set to null | C++-only `detail::FlatMap` (sorted vector) or ordinal-indexed arrays pointing into the bound storage, which stays; iteration orders that callers can observe (`StaticDoorWorld.getStaticDoors`, `TownSpawnMap.getTownSpawns`, `TownSpawn.getTownLevels`) are recomputed in Java's `HashMap<Integer>` order (`detail::javaIntegerHashMapValues`) | Bound templates are moved into reserved vectors only through noexcept moves, which the MSVC `std::map`/`std::unordered_map` lack; static-data.md §2.6 keeps the storage |
| Present but empty optional string attributes (`WalkerTemplate` `rows`, `Building` `parts_match`) | `null` when absent, `""` when present and empty: `WalkerTemplate` fails the load on `Integer.parseInt("")`, `Building.getPartsMatchTag` returns `""` | The generated member is a plain `std::string`, so an empty value counts as absent: `rows=""` makes the formation `POINT`, `parts_match=""` reads the holder's building (the binder logs a one-time warning for the empty value). `rows` with commas only gives an empty list like `String.split` | The binder cannot tell `""` from an absent attribute; neither form occurs in the data (the census finds only non-empty values). Test `WalkerTemplatesTest.StepsLoopTypesAndRows` |
| `NpcShoutData.afterUnmarshal` mutations of the shout templates | Copies the shouts per npc id, then `shoutList.getNpcIds().remove(j)`, `getNpcShouts().clear()`, `shoutList.makeNull()`, `group.getShoutNpcs().remove(i)` and `group.makeNull()` | `ShoutList`/`ShoutGroup` getters are const; `makeNull` is ported but destroys the bound `NpcShout` objects, so the holder (P4-09) builds its index from `const NpcShout*` into the bound lists in Java's visiting order and skips every remove, clear and makeNull | Templates are const after load and index maps point into the bound storage (static-data.md §2.6); the index content and order are Java's |
| Missing required lists in edge cases absent from the data | `ArcadeLevels.getMaxUpgradeLevel` and `StorageExpansionTemplate`'s getters throw `NullPointerException` when the (required) list was never bound; `MeshList.getZoneName` returns `null` for a mesh without `zone` | `ArcadeLevels` throws `IndexOutOfBoundsException`, `StorageExpansionTemplate` returns 0 / nullopt; `MeshList::getZoneName` returns `""` for a present mesh without `zone` | Bound lists are empty vectors, never null; the one `<levels>` element of arcadelist.xml has `<level>` children and every `<expansion_npc>` has `<expand>` children, and `MeshList` has no binder and no caller (Java does not use it either) |

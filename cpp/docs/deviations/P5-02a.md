### Fixed in the fixer run (review finding: raw float-to-int casts)

`HpUseAction.getCost` (`(int) (valueWithDelta / 100f * maxHp)`), `HpUsePeriodicAction.act` and `MpUsePeriodicAction.act` (`(int) (max *
(value / 100f))`) were written as `static_cast<int32_t>` of a float, which is undefined behaviour out of the int range (MSVC answers
`INT_MIN`). They now go through the saturating `javaFloatToInt` that Skill.cpp and MotionData.cpp use (NaN 0, `Integer.MAX_VALUE` /
`MIN_VALUE` beyond the range, JLS 5.1.3). Observable: with `value="2000000000" ratio="true"` Java's cost is `Integer.MAX_VALUE`, which nobody can
pay, where the old cast charged `INT_MIN` - `reduceHp` then clamped the caster down to 1 HP and the effect ran on. Tests (both failed before the
fix): `SkillConditionsTest.ARatioCostBeyondTheIntRangeSaturatesLikeJavasCast`, `APeriodicRatioCostBeyondTheIntRangeSaturatesAndEndsTheEffect`.

### Not a deviation: the critical proc of a bow is a stagger

`SkillEngine.createCriticalProcEffect` comments `case BOW -> id = 8217; // stun` (SkillEngine.java:211), and M5b-1's rows in P5-02.md called
it the stun arm. Skill 8217 "Stunned" has a single effect, `<stagger duration1="2000" .../>` (skill_templates.xml), so the proc is a
**`StaggerEffect`**, not a `StunEffect`; 8218 (POLEARM, STAFF, GREATSWORD) is a `<stumble>`, a `StumbleEffect`. The port keeps Java's comment;
the test is `CriticalProcEffectTest.BowCreatesTheStagger`.

P5-09 was split into P5-09a (drop, rewards, passport, bonus and faction packs, guide), P5-09b (trade and market: `TradeService`,
`ExchangeService`, `PrivateStoreService`, `BrokerService`, `services/trade`) and P5-09c (mail and craft) for M5c (m5c-plan.md D1, I-01). The
rows of the shared `P5-09.md` from waves 5a to M5b-3 stay there (among them `PricesService`'s long casts and `BrokerService`); this file holds
P5-09b's rows from M5c on.

### Java behaviour kept on purpose (pinned by the tests; the fixes are the user's)

- **D7, the double-confirm race** (`ExchangeService.confirmExchange`, ExchangeService.java:225-232): ported as Java has it and measured by
  T-04 in this stage (the four `BothPassTheCheck...` cases pinned it); the owner chose on 2026-09-27 to fix it, and the fix is a deviation of
  its own commit after stage 1: see "The D7 fix" below, which keeps the measurement.
- **`performTrade` does not undo a removal** (ExchangeService.java:248-252): when the second removal fails after the first succeeded, the first
  player's whole stacks stay out of the cube (their rows are unchanged, so a relog brings them back), and his split parts and kinah are lost.
  Test: `ExchangeTest.WhenTheOtherPlayersItemIsGoneTheConfirmingPlayersRemovalIsNotUndoneAsInJava`.
- **A refused line of a sale to an npc** (TradeService.java:194-244) returns after the earlier lines were taken and before anything is paid or
  listed for buy-back. Test: `TradeServiceTest.ARefusedLineLeavesTheEarlierLinesSoldUnpaidAsInJava`. (A line the daily sell limit cannot pay
  is different: it ends the list with a `break` (:223-226), so the earlier lines are paid and listed. Test, with the shipped
  `gameserver.limits.enable = true`: `TradeServiceTest.TheDailySellLimitCutsALineAndStopsTheListAtTheFirstLineItCannotPay`.)
- **A private-store stack the seller used up** (PrivateStoreService.java:152-160) stops the sale after the earlier rows moved to the buyer and
  before any kinah moved: those rows are the buyer's unpaid. Test: `PrivateStoreTest.AStackTheSellerUsedUpStopsTheSaleHalfWayAsInJava`.

## The D7 fix (the owner's decision of 2026-09-27; its own commit after M5c stage 1)

The owner answered m5c-plan.md D7 on 2026-09-27 (docs/design/owner-decisions.md): fix the double-confirm race, and record the fix. Stage 1 had
ported it as Java has it and measured it (T-04, §19.4 of the plan); the measurement is kept below.

| Area | Java | C++ | Reason |
|---|---|---|---|
| `ExchangeService.confirmExchange`, the two confirmations of one pair | `currentExchange.confirm()`, then `if (getCurrentExchange(currentPartner).isConfirmed()) performTrade(...)` (ExchangeService.java:225-232): a check-then-act on the plain fields `Exchange.confirmed`, so two `CM_EXCHANGE_OK` processed at once on the partners' connection threads can both pass the check and both run `performTrade` | After the check the confirmation takes the pair's key with a compare-and-set, trades only if it took it and the pair it confirmed is still the registered one, and gives the key back when `performTrade` has returned; a confirmation that finds the key taken returns after its `SM_EXCHANGE_CONFIRMATION(2)`. `// Deviation: D7` in `confirmExchange`, on the key set and in `performTrade` | The owner's decision: the second trade destroys split stacks, pays the kinah twice each way or releases the object id of a live item (measured below). An unraced exchange is unchanged (below) |

**What Java does** (measured in stage 1 on the fixture's `DeterministicExecutor`: B's `CM_EXCHANGE_OK` queued after its `confirm()` and run from
the exchange log line of A's first put, i.e. after A's `performTrade` removed both players' items and before it stored and cleaned up; the four
`ExchangeRaceTest.BothPassTheCheck...` cases pinned it until this commit):

- whole stacks on both sides: B's `performTrade` finds its item gone, audits "tried to trade not existing item" and "tried to exploit kinah
  exchange with partner", and ends both exchanges; A's trade completes and every item id is conserved - the cost D7 expected, but only for this
  mix;
- split stacks and kinah on both sides: B's `performTrade` succeeds too. Both removals run twice, each split copy is put once (the second put of
  the same object is refused by `ItemStorage.putItem`'s `putIfAbsent`), and the kinah moves twice each way: nothing is duplicated, but 30 of 150
  potions are destroyed and A pays 600 and gets 200 for an offer of 300 against 100;
- A's split stack against B's whole stack: B's `performTrade` fails on the sword, and its `cleanUpExchanges(true, B, A)` (:249, :273-274)
  looks for A's split copy in A's cube, where it no longer is (A's trade has put it into B's cube), and releases the object id of that live
  item. Java's `IDFactory.release` moves `nextMinId` down to the id (IDFactory.java:178-184), so the next `nextId()` hands it out again and two
  objects share it; the port's 300 s quarantine and monotone cursor (IDFactory.h) only delay that;
- A's whole stack against B's split stack and kinah: B's `performTrade` takes B's split part and kinah a second time, fails on A's potions and
  releases the id of B's split copy, which A's trade then puts into A's cube: 20 potions and 100 kinah destroyed, and a live item whose id is
  released.

**The fix** (ExchangeService.cpp, `confirmExchange`; no header changes, since `ExchangeService.h` and `Exchange.h` are frozen spine headers,
hub-headers.md §14):

- The pair's key is one of its two `Exchange` objects, the one of the player with the lower object id, so both partners' confirmations name the
  same object. `tradesStarted`, a file-local `runtime::ConcurrentKeySet<Ref<Exchange>>` (lock class `ExchangeService::tradesStarted#stripe`),
  holds the keys of the trades that run: membership is identity (`Exchange` has no Java `equals`), and the `Ref` keeps the object, and so its
  identity, alive while the key is taken. `add` is the compare-and-set; a scope guard gives the key back on every way out once it is taken:
  when `performTrade` returns or throws, and at the re-check's return.
- The check after taking the key (both players' registered exchanges are still the ones the confirmation read): the key is given back after
  the trade, so a confirmation that passed :230 before its partner's trade and takes the key only after it would otherwise run `performTrade`
  on whatever the map holds by then - nothing (a `NullPointerException` in `validateExchange`) or the pair's next exchange, whose offers nobody
  confirmed. `AConfirmationThatLostThePairNeverTradesItsNextExchange` reaches the second case and the four mix sweeps the first (mutant M2
  below). Either of its two comparisons alone is enough for D7: a trade's clean-up removes both players' exchanges (:262) while its
  confirmation still holds the key, so a confirmation that takes the key after that trade finds both changed. The second comparison only
  guards a pair that something else has half ended (a cancel racing the confirmation), which D7 does not cover; a mutant that keeps either
  comparison alone passes every test (R13 and R14 of the review).
- Not `Exchange.locked`, which stage 1 tried in the mutation runs: a real client locks (`CM_EXCHANGE_LOCK`) before it confirms.
- An unraced exchange is Java's: the confirmation that sees its partner confirmed finds the key free, and the added steps (a set insert and
  removal, two map reads) send and log nothing, so the packets, the messages, the order of the item and kinah moves and the log lines are
  unchanged. Every `ExchangeTest` case (among them the packet order of `TheSecondConfirmationTradesAndCleansUp`) and
  `ExchangeRaceTest.QueuedConfirmations*` pass unchanged.
- Still Java's, on purpose: a confirmation whose exchange its partner's trade ended between two of its own reads (:227 and :230 read the
  exchanges again after :220) throws a `NullPointerException`, which the packet thread logs; nothing changes state (the sweeps count these
  "late confirmations" and check how many there are). Two confirmations that each miss the other's `confirm()` (a store-load reordering the plain Java fields allow) leave
  a confirmed exchange untraded, as in Java. A cancel racing a trade (`cancelExchange` during `performTrade`) is another race than D7 and
  unchanged, as are D7's siblings in m5c-plan.md §8 (two buyers of one private store, a mail recipient deleting during a delivery).

**Why the observer fix sits in `ObserveController.cpp`** (the options of the research report, weighed):

- *A hand-written `ObserverType` constant* (Java's natural fix: an `ITEM_USE_INTERRUPT` mask next to `ALL`) is not possible without Java:
  `generated/.../controllers/observer/ObserverType.h` is generated by `tools/xmlgen` from ObserverType.java ("do not edit"), with an
  `EnumTraits` names table of exactly the Java constants, and its hand-written companion `ObserverTypeInfo.h` asserts one mask per constant
  (`static_assert(ALL + 1 == OBSERVER_MASKS.size())`). A C++-only enumerator would need an out-of-range `static_cast<ObserverType>(20)`, which
  the names table and the assertion do not cover.
- *A virtual mask on `ActionObserver`* would change a hub header (the vtable of every observer, every includer recompiled) for one class.
- *Re-attaching in `ItemUseObserver`'s three hooks* needs an owner reference the base class does not have, and between the removal and the
  re-attach a concurrent `abortItemUseObservers` (CM_CASTSPELL, CM_EQUIP_ITEM, CM_TUNE) would not see the observer.
- The chosen matching function touches no header and changes nothing for any observer but an `ItemUseObserver`, and for it only the three
  notifications whose hooks are empty (no subclass overrides them, in either tree: checked with grep), so the only visible difference is that
  it stays attached. The dynamic type is asked only for an ALL observer and only on the three notification types.
- **Every ported item use changes the same way, not only identification and tuning.** No `ItemUseObserver` is added with `addObserver`: each
  one is attached, as in Java (`attach`: soul binding, Equipment.cpp:184 / Equipment.java:744; identification, ItemActionService.cpp; tuning,
  TuningAction.cpp; decomposition, DecomposeAction.cpp; enchanting, EnchantItemAction.cpp; extraction, ExtractAction.cpp; socketing,
  ItemSocketService.cpp; quest start, QuestStartAction.cpp; reading, ReadAction.cpp). So in each of them an HP tick, an abnormal state or a
  summon release during the use no longer detaches the observer, and a later move, hit, equip, sit or skill cancels the use with its own
  message and animation; for soul binding that is `STR_SOUL_BOUND_ITEM_CANCELED` and the animation (0, 8), where Java would bind the item
  anyway. That is the intended correction. StigmaService's observer (StigmaService.java:376-387) is `AION_UNPORTED` and gets the same
  matching when it is ported.
- **Gathering is left alone**: `GatheringTask`'s gatherer observer (GatheringTask.java:137-165, attached at :55; C++ `GatheringTask.cpp`) is
  the only other one-time ALL observer, not an `ItemUseObserver`, and has the same flaw (an HP tick detaches it, and moving no longer aborts
  the gathering). `CM_GATHER` is not ported (M5c D10 / M5d D13: after quests), so it is unreachable; revisit it when gathering lands. The other
  ALL observers (`StanceObserver`, `AbstractQuestZoneObserver`) are added permanently and never consumed.

**Charge skills (report 2's caveat).** While a skill charges, `Creature.canAttack` is false, so a charged "ability" would refuse CM_ATTACK too.
It was not one here: `CM_USE_CHARGE_SKILL` was not ported then (m5e-plan.md C-04; ported 2026-10-01, P5-16.md), and the factory warns once per process the first time a client
sends it. The session's only warning is Zatsuko's at 19:56:29, while Rectangle (the report's character) played from 18:11:56 until 18:32 in the
same process, so Rectangle never released a charge skill.

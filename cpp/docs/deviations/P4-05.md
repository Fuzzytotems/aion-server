## Fix 2026-11: CompressUtil links zlib (owner's decision, lane B, branch `fix/cpp-zlib`)

**The bug:** the hand-written inflater of `CompressUtil::decompress` decoded every distance of a fixed Huffman block (BTYPE 01) as distance 1:
its table builder (`construct`, after puff.c) treated the 30 five-bit fixed distance codes as an incomplete set and returned before it filled
the symbol table, and `fixed()` ignored the result. Stored and dynamic blocks decoded correctly, so most tests passed; a script that
zlib compresses into a fixed block with back-references (zlib picks fixed codes for short inputs) came out wrong and failed the Adler-32 check
("incorrect data check"). `PlayerScripts.set` then dropped the script, so stored house scripts never loaded
(`LegionHouseItemDaoTest.HousesBidsAndScripts` skipped).

**The fix:** the owner chose to link zlib (vcpkg port `zlib`, `find_package(ZLIB)`, `ZLIB::ZLIB` on `aion_gs_base`) instead of repairing the
port. `CompressUtil.cpp` is now CompressUtil.java at 51d7a19cb over zlib, as java.util.zip is:

| Area | Java | C++ | Reason |
|---|---|---|---|
| `compress` | `Deflater()` (level 6, zlib wrapper, windowBits 15, memLevel 8, default strategy), `finish()`, `deflate` into a 1024-byte buffer until `finished()` | `deflateInit2(Z_DEFAULT_COMPRESSION, Z_DEFLATED, 15, 8, Z_DEFAULT_STRATEGY)`, `deflate(Z_FINISH)` into a 1024-byte buffer until `Z_STREAM_END` | the same bytes: Java bundles zlib; the vectors of zlib 1.3.1 (Python) match vcpkg's zlib 1.3.2 |
| `decompress` | `Inflater()`, `inflate` (zlib, `Z_PARTIAL_FLUSH`) into a 1024-byte buffer; `count == 0 && finished()` ends the loop, any other 0 throws `RuntimeException("Bad zip data, size: N")` | the same loop over `inflateInit` / `inflate(Z_PARTIAL_FLUSH)`; `Z_DATA_ERROR` throws `IllegalArgumentException(strm.msg)` (Java: `DataFormatException`), `Z_NEED_DICT` and `Z_BUF_ERROR` write 0 bytes, so a stream that needs a dictionary or ends early throws `IllegalStateException("Bad zip data, size: N")` | the existing exception mapping; bytes after the end of the stream (the client's 8 trailing bytes) are ignored, as `Inflater.finished()` ends Java's loop |
| `Z_MEM_ERROR` / other zlib failures | `OutOfMemoryError` / `InternalError` | `std::bad_alloc` / `IllegalStateException` with zlib's message | no Java Error types |

The hand-ported deflate and inflate (about 1000 lines) and their zlib license note are gone. Tests: `CompressUtilTest.HouseScriptBlocks`
(tests/base/UtilsTest.cpp: the fixed-block row of the DAO test, a real lbox script compared with Python's `zlib.compress(script, 6)`, and
the block with the client's 8 trailing bytes), `HouseModelTest.PlayerScriptsAcceptARealScriptBlockWithTheClientsTrailingBytes`,
`LegionHouseItemDaoTest.HousesBidsAndScripts` without its skip (and a stored block with the trailing bytes loads), and the M5h gate's
`houseScript` now sends a zlib block with the trailing bytes instead of a stored block (C18 reads the stored blob as hex).

### Ported outside the planned subset (stage 2)

`AbstractCraftTask` (new), `GatheringTask` (new), `AbstractCraftTask_CraftTypeInfo.h` (new), `AbstractInteractionTask::start/stop/abort/
isInProgress`, `Skill`'s three constructors, `Skill::initializeSkillMethod`, `Skill::getSkillId` and `Skill::isPassive`. The last three were on
the list because the constructor and `PvpService` were the two `C4702` "unreachable code" warnings of the checked RelWithDebInfo gate build that
belong to this lane (scenario-lane change request, m5a-plan.md §5.10); porting the bodies removes them without a pragma.

### Not a deviation: a throwing interaction body (stage-2 fixer run)

A review finding proposed a C++-only breaker for `AbstractInteractionTask`, on the assumption that a throwing `onInteraction` ends the periodic
`Future` as FAILED and leaves `task` -> `Future` -> body -> task alive because `stop()` never runs. It does not: `ThreadPoolManager.scheduleAtFixedRate`
wraps the runnable in `RunnableWrapper(..., catchAndLogThrowables = true)` (ThreadPoolManager.java:60-62), so in Java the exception is logged
inside the body and the periodic task is re-armed, and `Future` does exactly the same here (`logExceptions`, Future.h:89, `invokeBody` reports
`failed = false`). A throw therefore never bypasses a later `stop()`, and cancelling releases the captures (`Future::cancel` ->
`releaseCaptures`), so the handle left in the field after an external cancellation retains nothing. `runInteraction` and `stop` stay Java's;
both facts are now recorded as comments there.

`GatheringTask` calls `GatherableController::completeInteraction` (from `onInteractionFinish`, GatheringTask.java:50) and `rewardPlayer` (from
`onSuccessFinish`, :83), which P4-11b ported; the two remaining `AION_UNPORTED` bodies of that controller (`startGathering`'s tail and
`getGatheringPlayerId`) were the P4-11b owner's to close now that this header exists. **Both are closed**: the stage-3 fixer run drives the real
`startGathering` and reads `getGatheringPlayerId` in `InteractionTaskTest.TheControllerStartsAGatheringThatRunsToItsFailureFinish` (the call
chain changed only in this file's tests, not in the controller).

## Wave 5a, stage 3 (code-findings lane)

### Kept Java races (`// java-race`, design decision D6)

`AbstractInteractionTask::start` and `AbstractInteractionTask::stop` carry a `// java-race` marker (runtime-architecture.md §3.7,
docs/design/conventions-game-server.md): both guards are Java's unsynchronized check-then-act on `Player.interactionTask`
(`AbstractInteractionTask.java:61-64` and `:84-85`), and the lock-per-operation `Field` makes each read and each write safe without making the
pair atomic. `PlayerLeaveWorldService.java:125-126` (`if (player.getInteractionTask() != null) player.getInteractionTask().abort()`) is the same
pattern in another chunk and is not marked yet; it is listed in the stage-3 report for the P5-07 owner.

**What the cycle is, and what is not claimed about it** (rewritten in the stage-3 fixer run). `Player.interactionTask` is a
`Field<Ref<AbstractInteractionTask>>` and `AbstractInteractionTask.requester` is a `const Ref<Player>`, so the two form a reference cycle that
Java's garbage collector reclaims and refcounting does not. The only hook that cuts it is the guarded write above:
`generated/concurrency/cycles.toml` resolves `com.aionemu.gameserver.model.gameobjects.player.Player.interactionTask` as
`java-hook: AbstractInteractionTask finish / abort call requester.setInteractionTask(null) (AbstractInteractionTask.java:85; leaveWorld aborts
it)`. When the guard loses its race — a concurrent `start()` replaced the field between this task's read and its write — the losing task skips
the clearing and the field keeps naming the task that replaced it.

An earlier version of this section went on to state, as fact, that the cycle therefore survives `leaveWorld` and leaves **a stale `Player` across
a relogin**, visible as a non-zero `Player` row of `live_counts.txt` (§5.7 Q8). That consequence was never reproduced, the stage-3 review could
not construct the interleaving, and the code points the other way, so it is **withdrawn**: every write that stores a task comes from a `start()`,
which schedules the periodic run immediately afterwards; every run begins with `!requester->isOnline() || onInteraction()`
(`AbstractInteractionTask.java:69`); and `PlayerLeaveWorldService.java:65` (`PlayerLeaveWorldService.cpp:87`) nulls the client connection —
"this sets the player semi-offline" — before `:125-126` aborts the interaction task. Whichever task the field names after a logout therefore
stops itself on its next run, and that `stop()` then does find itself in the field and clears it. The race is real and kept; the consequence
claimed for it was not.

Fixing the race (an atomic compare-and-set of `Player.interactionTask`) would need a signature change on the frozen `Player.h` and would change
the behaviour of concurrent `start()` calls, so it is kept and documented per D6.

### The shape that does keep the cycle: a throwing `onInteractionStart`

`start()` writes `requester.setInteractionTask(this)`, then calls `RecallService.cancel` and `onInteractionStart()`, and only then schedules the
periodic run (`AbstractInteractionTask.java:64-77`). A throw in that window leaves the field naming a task that will never run, so nothing but an
explicit `stop()` cuts the cycle — the sibling of the throwing periodic body of m5a-plan.md §10.5, and, like it, exactly what Java does (its
garbage collector reclaims the cycle afterwards, which refcounting cannot). The port is faithful, so this is a fact, not a deviation. Test:
`InteractionTaskTest.AThrowingOnInteractionStartLeavesTheTaskInTheField` (the field still names the task, no run ever stops it, `stop()` cuts it).
No M5a path throws there: `GatheringTask::onInteractionStart` sends packets and attaches the gatherer observer, and `CheckOutput::zeroLiveClasses()`
lists `Player`, `AbstractInteractionTask` and `GatheringTask`, so a run in which it happened would fail the gate through its own ERROR line.

### Gathering runs to completion in a test

Two tests drive a real `GatheringTask` through `ThreadPoolManager` until it ends. Both give the player one accepted, real `AionConnection` from a
loopback `NioServer` (`TestClientLink` in the test file; `tests/network/support/GameServerTestServer.h` is the test support of P4-15 and not on
this chunk's include path), because the scheduled body is `!requester.isOnline() || onInteraction()` (`AbstractInteractionTask.java:69`) and
`Player.isOnline()` is `getClientConnection() != null` (`Player.java:348`), so every earlier test stopped the task on its first run without
reaching a single `GatheringTask` body.

- `InteractionTaskTest.AGatheringTaskRunsToItsFailureFinish` builds the task by hand with `skillLvlDiff = -1`, so `analyzeInteraction` fills the
  failure bar on the first run and the second run takes `onFailureFinish`. Only a hand-built task reaches that branch:
  `GatherableController::checkPlayerSkill` refuses a player below the template's skill level, so a gathering started through the controller never
  has a negative difference.
- `InteractionTaskTest.TheControllerStartsAGatheringThatRunsToItsFailureFinish` (stage-3 fixer run) takes the real entry point,
  `GatherableController::startGathering`, with the harvest skill at exactly the template's level (difference 0) and
  `CraftConfig::MAX_GATHER_FAILURE_CHANCE` at 100 for the scope of the test, which makes every `analyzeInteraction` fail (`Rnd::chance()` is
  `[0, 100)`), so the failure bar fills in eight runs and the ninth finishes the interaction. **This is the test that covers
  `GatheringTask::onInteractionFinish`**: with the task registered in the controller, `getGatheringPlayerId()` is the gatherer's object id before
  the finish and 0 after it (`completeInteraction`), and `ObserveController::hasObservers()` is true before and false after (the observer
  removal). The hand-built test asserted neither: its task is not the one the controller holds, so `getGatheringPlayerId()` was 0 either way, and
  `notifyMoveObservers()` on an already stopped task changes nothing whether the observer is still attached or not.

The success branch still needs `ItemService.addItem` and a `WorldMapInstance` with an instance handler and stays out of a unit test.

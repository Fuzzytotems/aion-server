## Wave 5b-2, stage 1 part 3 (attack-effects lane, m5b2-plan.md F-06, decision D12)

short-circuit and float operation is Java's, in Java's order: the int products `baseAttack * skillDamage` and `accMod1 * level` wrap

`ProcAtkInstantEffect`) are `dynamic_cast`s. Tests: `tests/stats/SkillDamageTest.cpp`, 22 cases of hand-derived golden vectors.

**Pinning the float order (risk 11).** Most vectors are exact in float, which cannot tell two orders of the same operations apart. The fix
step added inexact vectors, found with a scratch model of Java float arithmetic (every binary32 operation evaluated exactly and rounded once),
so that the reordered expression truncates to another int, or lands one float step away where the body answers a float: the knowledge
factor summed before it multiplies, the MDef tenth `/ 10f` (MDef 203) and the PDef tenth `/ 10` (PDef 104), movement before the one-time
multiplier, rnddmg before the critical, the npc owner AI and the shared divisor before the PvP/PvE modifiers, and the dot's multiplier
before its critical. The same step pinned the accuracy formula with exact replayed parry counts at two skill levels (instead of a rate
cancelled to 0, which the swapped forms `accMod1 + accMod2 * level` and `(accMod2 + accMod1) * level` also reached), the dot's element and
floor order, the PDef tenth before block/parry, the target's movement on its PDef and MDef, the `&&` of the dirty fix, the default arm's
magical attack, the SummonedObject baseAttack, the wrapping `baseAttack * skillDamage`, the weapon group of an element-less dot critical,
and the npc roll taken from the float damage.

## Audit 2026-09-23, finding M-1 (the "most hated" ranking under concurrent hate changes)

`AggroList::nthMostHated` sorted the valid entries with a comparator that re-read each entry's live `AggroInfo.hate` (a `runtime::Field`, one
atomic load per read) while packet threads (`addDamage`/`addHate`), `AggroNotifier` and the 10 s hate reduction task change it without a common
lock. When the order of two entries flipped between two comparisons, MSVC's `stable_sort` (an unguarded insertion sort below 33 elements) walked
before `begin()`: an access violation or an out-of-bounds write in a release build, a stale-borrow `IllegalStateException` (or the Debug
"invalid comparator" abort) in the checked build, which leaves the npc in FIGHT with no swing scheduled. Every npc swing
(`SimpleAttackManager.attackAction`) and chase tick (`AttackManager.targetTooFar`) with two or more hated attackers ran it.

| Area | Java | C++ | Reason |
|---|---|---|---|
| `AggroList.getTarget(MOST_HATED / SECOND_MOST_HATED / THIRD_MOST_HATED)` under concurrent writers | `stream.max(comparingInt(AggroInfo::getHate))` and `stream.sorted(comparingInt(AggroInfo::getHate).reversed())`: every comparison reads the live hate, so a concurrent change can give an order no single moment had, and at worst TimSort throws `IllegalArgumentException` ("Comparison method violates its general contract", never below 32 elements); never memory corruption | Each valid entry's hate is read **once** into a `(entry, hate)` snapshot in encounter order; MOST_HATED is the first strict maximum of the snapshot, SECOND/THIRD a `std::stable_sort` of the snapshot by the snapshotted hate (Java's reversed comparator, ties in encounter order). A consistent order, so the answer is always an element of the list | A C++ sort whose comparator answers inconsistently is undefined behaviour. For a list nobody changes during the call the answer is Java's (same comparator, same tie order); under concurrent writers both answer one of the entries, and only which one may differ, which Java does not define either. `streamValidTargetInfo` still reads the live hate for its `> 0` filter, as Java does, so an entry that passed the filter may rank with a snapshot of 0 or less, as in Java. Tests: `CombatDamageTest.GetTargetBreaksHateTiesByTheEncounterOrderOfTheAggroList` (the ranking and ties against Java's comparators), `CombatDamageTest.GetTargetStaysInsideTheAggroListWhileOtherThreadsChangeTheHate` (2 s of rankings against a thread flipping one entry's hate around another's by plain stores and a thread flipping a second through `addHate` and removing and re-adding a third; with the old live comparator it failed in each of 9 runs, in one of two ways: 4 runs hit the Debug CRT assertion "invalid comparator" (xutility), which aborts the test binary, and 5 threw the stale-borrow exception for the element before `begin()` after about 144 to 171 rankings) |

The other orderings of the class and of the AI target selection were checked for the same defect and do not share it: RANDOM and
RANDOM_EXCEPT_CURRENT_TARGET filter and draw (no comparator; L-10's objectId comparison is a separate, latent finding), `DamageList.getMostDamage`
and `TeamDamageList.getMostDamage` scan values the list copied at construction, and the four callers (`SimpleAttackManager.cpp`,
`AttackManager.cpp`, `GeneralNpcAI.cpp`, `AbstractAI.cpp`) only call `getTarget(MOST_HATED)`. `MaxCountProperty` already sorts snapshotted
distances.

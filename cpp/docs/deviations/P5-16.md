# P5-16 client packets L-Z: deviations

## M5b-2, stage 1 part 1 (player-side lane, m5b2-plan.md P-03)

`CM_REMOVE_ALTERED_STATE` is a **new file**: CM_REMOVE_ALTERED_STATE.java:23-42 statement for statement (`readUH` skill id and two `readC`;
`findBySkillId`, the DEBUFF audit line, otherwise `endEffect`). **No behavioural deviation.**

| Area | Java | C++ | Reason |
|---|---|---|---|
| `" (effector: " + effect.getEffector() + ")"` | `String.valueOf`: `"null"` for a null effector | `effector ? effector->toString() : "null"` | String concatenation of a reference, spelled out as `PlayerRestrictions::checkFly` does for the target |
| `CM_REMOVE_ALTERED_STATETestAccess` | - | C++ only: a `friend struct` declared in the header, defined in `tests/cm_lz/RemoveAlteredStatePacketTest.cpp`, reads the decoded skill id | Java's field is private; until `EffectController::findBySkillId` is ported (m5b2-plan.md K-02) `runImpl` cannot show it |

**Where the packet stops today**: at `EffectController::findBySkillId`, `AION_UNPORTED` until K-02. A real client can only send it by
right-clicking an effect icon, and no effect exists before the effect engine, so it is not reachable in play before K-02 lands.

### Not ported on purpose (m5b2-plan.md P-03, **W**)

`CM_TOGGLE_SKILL_DEACTIVATE` and `CM_USE_CHARGE_SKILL` have no C++ file and stay unregistered, because their paths are not ported and no
level-1..10 skill of a starting class is a toggle, a stance or a charge skill:

- `CM_TOGGLE_SKILL_DEACTIVATE` (43 Java lines) needs `EffectController::removeEffect(int32_t)` (`AION_UNPORTED`, K-02) - called once
  directly and once more through `PlayerController::stopStance` - and, to have anything to deactivate, a toggle or stance skill that
  `Skill::useSkill` (S-02) started. Everything else on its path is ported: `SkillData::getSkillTemplate`, `SkillTemplate::isToggle`/`isStance`,
  `AuditLogger::log`, `PlayerController::getStanceSkillId` and `stopStance`.
- `CM_USE_CHARGE_SKILL` (32 Java lines) needs `standins::chargeSkillGetAndUse` gone (m5b2-plan.md P-04, second half), i.e.
  `SkillEngine::getChargeSkill` (`AION_UNPORTED`, S-01) and `ChargeSkill::useSkill` (S-07), and a charge skill that is casting, i.e.
  `Skill::useSkill` (S-02). `Player::getCastingSkill`, `SkillTemplate::isCharge`, `Skill::getCastStartTime` and `CreatureController::useChargeSkill`
  up to the stand-in are ported.

## M5b-3, stage 1 (player-side lane, m5b3-plan.md P-05)

Seven **new files** with their `AION_CLIENT_PACKET` markers, each statement for statement: `CM_START_LOOT` (opcode 154, CM_START_LOOT.java:34-54),
`CM_LOOT_ITEM` (155, :22-34), `CM_USE_ITEM` (37, :37-125), `CM_MOVE_ITEM` (156, :24-36), `CM_SPLIT_ITEM` (157, :26-40), `CM_REPLACE_ITEM` (178,
:24-36) and `CM_MANASTONE` (74, :38-108). **No behavioural deviation.**

| Area | Java | C++ | Reason |
|---|---|---|---|
| `CM_START_LOOT`'s warning `player + " sent unknown loot action type " + action` | `String.valueOf(player)`, the byte as a signed number | `player ? player->toString() : "null"`, `std::to_string(action)` of the `int8_t` | String concatenation spelled out, as `CM_REMOVE_ALTERED_STATE` does |
| `CM_USE_ITEM`'s `canAct(player, item, targetItem, x)` / `act(...)` for `DyeAction`, `MultiReturnAction`, `InstanceTimeClear` | one vararg: the `HouseObject` (null when none), the Integer return index, the Integer sync id | `{std::any(Ref<HouseObject>)}` (null for Java null), `{std::any(int32_t)}` | The params contract of `AbstractItemAction.h` (m5b3-h01). The three actions' bodies are `AION_UNPORTED` (m5b3-plan.md D6), so the parameter is not observable yet |
| `CM_USE_ITEM`'s action list | `getActions() == null ? Collections.emptyList() : getActions().getItemActions()` | a vector of `const AbstractItemAction*` borrowed from the static data | The actions are immortal templates; `instanceof` is a `dynamic_cast` |
| `CM_MANASTONE`'s `new EnchantItemAction()` (:79) | a fresh default-constructed action per packet | one function-local `static const EnchantItemAction` (value-initialized), shared by every packet | The action holds nothing mutable, so one instance answers as every fresh one does; unlike a stack object it outlives a task or observer its `act` may create (M5c) the way a bound template does |
| `CM_*TestAccess` | - | C++ only: a `friend struct` in each header, defined in the tests, reads the decoded fields | Java's fields are private (package-private for `CM_SPLIT_ITEM`, private here: nothing else reads them) and have no getters |

**Where the packets stop today.** `CM_MANASTONE` arms 1 and 2 construct the `EnchantItemAction` and ask `canAct` (`AION_UNPORTED`, M5c, D8),
a stigma pair reaches `StigmaService::chargeStigma`, arm 3 `ItemSocketService::removeManastone` and arm 8 `EnchantService::amplifyItem` (all
`AION_UNPORTED`, M5c); arm 4, the godstone, is complete. `CM_USE_ITEM` reaches every action's `canAct`; only `SkillUseAction` is ported, so an item
with any other action throws there (D6). The other packets reach ported bodies on the solo path, and unported ones on these:

- `CM_MOVE_ITEM` and `CM_SPLIT_ITEM` for a legion member moving or splitting into or out of the legion warehouse: `ItemMoveService`
  (ItemMoveService.cpp:73) and `ItemSplitService` (ItemSplitService.cpp:103, :117) call `LegionService::addWHItemHistory`, whose
  `addHistory` is `AION_UNPORTED` (LegionService.cpp:387-389; m5b3-plan.md §2.8 E-9, M5h).
- `CM_START_LOOT` and `CM_LOOT_ITEM` for a team member: `DropService`'s team arms ask the corpse's `LootGroupRules`, whose 7 bodies are
  `AION_UNPORTED` until M5g (D9).

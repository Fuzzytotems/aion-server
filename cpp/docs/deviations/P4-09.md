**M5b-3 stage 1 (2026-09-24).** The DEVIATIONS.md row `QuestDrop.questId` said the holder sets the id while loading; until this stage no code did,
so every `<quest_drop>` kept a null id and, once `registerDrop` was ported, `QuestService::isQuestDrop` threw a NullPointerException on every
kill of an npc with a quest drop (e.g. 210668 on Poeta). `QuestsData::afterUnmarshal` now sets each drop's id to its quest's id before the
holder is published (QuestEngine.java:89 semantics), through a `const_cast` on the holder's own non-const storage. Written by the M5b-3 loot
lane outside its chunk and accepted by the integrator (m5b3-plan.md §16); the test is
`tests/quest/QuestDropTest.cpp` `TheHolderGivesEveryQuestDropItsQuestIdAndInitRegistersItForTheKill` (210668 → 1108, 210671 → 1001).

**Cost when off** (the review's note, not a defect): each valid packet reads the config value once. That read is
`std::atomic<std::shared_ptr>::load`, which MSVC's STL implements with a short spin lock on the value and a reference count increment and
decrement. The packet processor threads share it, but it is small next to a packet's own work. A `std::atomic<bool>` kept at bind time would
make it one relaxed load, but it would also need a hook in `ConfigValue::set` (the tests and a config reload set the value), so the trace
keeps the plain snapshot read.

## Play-session diagnostics 2026-09-29: the server packet trace (the Sanctum crafting benches)

A second **C++-only diagnostic**, no behaviour change. In the owner's session of 2026-09-29 the crafting benches of the Artisans Hall in
Sanctum (static objects, `spawns/Statics/110010000_Sanctum.xml`, shown by `PlayerController.see` with `SM_GATHERABLE_INFO`) appeared about
10 s after the owner walked in, while npcs such as Diana, the alchemy master, showed at once. An earlier read-only investigation found the
packet's bytes, opcode and data equal to Java's. A second one compared **when** Java and C++ find a static object, and found no server-side
path that delays it:
- Every CM_MOVE calls `World.updatePosition(..., true)`, which updates the player's known list synchronously at the end of the call (Java
  CM_MOVE.java:143, World.java:234-235; C++ CM_MOVE.cpp:132, World.cpp:312-313). `KnownList.update` is a synchronized forget-then-find with no
  throttle, lazy flag, distance condition or periodic task (KnownList.java:43-46; KnownList.cpp:68-73). The server's own move loops pass
  `false` and never update a known list.
- `findVisibleObjects` scans the neighbour regions once, npcs and statics in the same loop with the same 95 m test, and never asks whether a
  region is active (KnownList.java:169-196, :212-216; KnownList.cpp:262-301).
- A static's `PlayerAwareKnownList` is aware of players only and never updates after the spawn (StaticObjectSpawnManager.java:32, :38;
  StaticObjectSpawnManager.cpp:39, :46), so only the player's own update finds it. An npc has two more triggers of its own, region activation
  (ActivateEventHandler.java:15, .cpp:14) and a walk's target reached (WalkManager.java:144, .cpp:163), which add both sides. They can make an
  npc appear earlier than the player's next update, never a static later.
- `MapRegion.add` → `activate()` only flips the region flags and hands `notifyCreatures` to the thread pool (MapRegion.java:64-67, :93-101;
  MapRegion.cpp:89-92, :133-146); the player's list is then updated on the CM_MOVE thread. A slow `notifyCreatures` (5-9 s in loaded Debug
  gate runs) cannot delay it, and client packets run on the connection's own packet processor, not on that pool.
- The C++-only parts of these paths (the striped pair locks of `KnownList::addPair`, whose see notifications run after the lock; the
  iteration order of the C++ `ConcurrentHashMap`) change no timing beyond one update.

So a delay of seconds is not plausible from the server code, in Java or C++. What the code allows is the same in both: an object is sent only
when a CM_MOVE puts the player within 95 m of it, so a bench farther away than Diana appears at the first CM_MOVE after the owner came within
range of it; or the client draws its level objects late on its own. The code cannot tell these apart, so the server now logs, on request,
when it sends a packet: the next session can time `SM_GATHERABLE_INFO` against the `CM_MOVE`s of the client packet trace.

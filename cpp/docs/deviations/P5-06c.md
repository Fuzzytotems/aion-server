# P5-06c the XML quest templates: deviations

P5-06 was split into P5-06a (the engine), P5-06b (the handler base) and P5-06c (the XML templates) for M5d (m5d-plan.md D1, item I-01). The
rows of the shared `P5-06.md` from wave 5a and M5b-3 stay there; this file holds the XML-templates lane's rows from M5d on. No part may edit
`P5-06.md` (`chunks.py check-ownership` allows a chunk only its own `docs/deviations/<chunk>.md`), so a lane that closes or changes one of its
rows says so here and the integrator edits the shared row when it merges the lane.

**Behaviour kept from Java that may surprise.** `ReportToMany.rewardStatusFromRewardNpc` is one flag of the handler, not of a player: a
`SET_SUCCEED` of any player makes every later talk to the quest's end npc in REWARD show the report page first (ReportToMany.java:34, 120-122,
139-140); tested by `SetSucceedAtAStepNpcRewardsAndTheEndNpcShowsTheReportPage`. A data-driven kill answers false unless it ends the step,
after it has updated the vars (MonsterHunt.java:183-238). `ItemCollecting` takes the work item on any action at the end npc in REWARD, before
`sendQuestEndDialog` (:154-161). 1842, 1843 and 1844 count 80 kills in vars 0-1 and their boss kill in var 1, so the first row's 64th kill
fills the boss row (the boss kill then counts nothing) and a boss kill before it adds 64 to the first row's total (`oracle.py m5d-quest
--quest 1842`'s kill run; not tested beyond the carry itself, which `AKillCountAbove63CarriesIntoTheNextVar` asserts on 1839).

**Not asserted, and why:**
- Branches no quest of the data reaches (measured over the 89 quest_script_data files): `ReportTo`'s `startDialogId` (no `report_to` row
  has `start_dialog_id`); `MonsterHunt`'s `rewardNextStep` (34 rows have `end_reward_next_step`, all data-driven, and only the old-style path
  reads it), `aggroNpcIds` with `onAddAggroListEvent` and the aggro branches of the kill and the REWARD dialog (no `aggro_start_npc_ids`),
  `startDistanceNpcId` with `onAtDistanceEvent` (no `start_dist_npc_id`), the work item taken in REWARD (9 rows have a work item, none
  data-driven or with aggro npcs, so the branch is never entered); the `FACTION` clause of `MonsterHunt` and `ItemCollecting` (all 106 and
  68 FACTION rows of the two kinds have no start npc, so `startNpcIds.isEmpty()` already holds); `ItemCollecting`'s `questMovie` and
  `checkOkDialogId`/`checkFailDialogId` (no row has `movie`, `check_ok_dialog_id` or `check_fail_dialog_id`); `ReportToMany`'s `mission`
  (`registerOnLevelChanged`, `onLevelChangedEvent`) and the npc movie (no row has `mission` or an `npc_infos` `movie`).
- `MonsterHunt.onEnterWorldEvent` past its vortex lookup, and `searchOpenRift` (6 rows with `invasion_world`: 39005, 39007, 39009, 49005,
  49007, 49009; worlds 210060000 and 220050000) - **reachable by the data and untested**. The registration is asserted
  (`AnInvasionQuestIsAskedAboutEveryEnterWorld`: 39005 is asked about the enter world of a Poeta player and fails on the unpublished
  `VORTEX_DATA`, which the engine logs), but the world check, the vortex and the open-rift start are not: `VortexLocation::setActiveVortex`
  is still `AION_UNPORTED`, so no active vortex can be made, and an open rift needs `RiftService`'s locations and a player in one of the
  two worlds, which the Poeta fixture does not have. **For the integrator (the D3 join):** once registered, these six run on every enter
  world of every player and call `VortexService::getLocationByWorld` before the world check (MonsterHunt.java:250), so every process that
  registers them must have `VORTEX_DATA` published (the server and the gates load all static data), and `RiftService`'s locations must be
  initialized (GameServer does it at startup) before a player enters one of the two worlds: the C++, like Java, throws NullPointerException

**Mutation proof.** 187 mutants of the eleven files (the five templates, `AbstractTemplateQuestHandler.cpp` and the five `register_`
bodies), each applied, built, restored and sha256-checked before its tests ran (`aion_gs_quest_tests --gtest_filter=*TemplateTest*`):
180 killed, the 7 equivalent ones above survive. Every one of the 369 assertions of the four test files is failed by at least one of the
killed mutants (a coverage script over the recorded failure lines). That measures each assertion, not the behaviour covered: the review of
this lane found 13 behaviour mutants on data-reachable paths that all 38 cases survived (the carry of a count over 63, the report over
every kill row, a data-driven step's totals over several rows, the item check at var 1, several work items, the invasion registration).
The fix round closed them with the cases above and proved them on a mutant schemata, each mutant switched by `AION_MUT`: the five template
files copied with 25 mutants (the review's 18 ids without its equivalent kill mutant, a report bound `>` to `>=`, a 7-bit var mask on the
kill, `validateAndRemoveItems` answering false, a `SETPRO` step of two, and a throw on the not-startable or held-already path of the zone
start of both kinds and of `ReportOnLevelUp`), compiled with the build's own flags and linked into a separate executable ahead of
`aion_gs_quest.lib`, so no production file was touched. Before the new cases the review's 13 behaviour mutants and the three throws
survived; after, 25 of 25 are killed, and each of the 53 new or changed assertion lines (the three helpers' error checks included) is
failed by at least one of them.

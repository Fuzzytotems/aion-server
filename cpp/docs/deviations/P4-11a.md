Corrected in stage 3: that row is about the classes that use `SummonedObject`'s own `setupStatContainers` (`SummonedHouseNpc`, `Kisk`,
`GroupGate`). `Homing`, `Servant` and `Trap` **override** it and their overrides are still `AION_UNPORTED`, because Java installs
`HomingGameStats`, `ServantGameStats` and `TrapGameStats` and none of the three has a C++ header yet (P5-01). Constructing one therefore still
throws out of `postConstruct`. Substituting `SummonedObjectGameStats` would not be faithful: `HomingGameStats` and `ServantGameStats` derive it
but override `getStat`/`getMBoost` with their own rates, and `TrapGameStats` derives `NpcGameStats`, not `SummonedObjectGameStats`
(`TrapGameStats.java:14`). No M5a path creates a homing, servant or trap (they come from skill effects, M5b), so the three bodies stay unported
until P5-01 delivers the three stat containers.

No deviation is left in this chunk for the master name of `SummonedHouseNpc`, `Trap`, `Homing` and `Servant`: `Npc::getMasterName()` reports the
`Field<std::string>` value `""` as `std::nullopt`, so without those overrides `SummonedObject::getMasterName` would substitute the creator's name
where Java (whose field is the empty string, not null) returns `""`. The overrides are what keeps the port faithful; they are listed under header
request `objects-1` and stay until the field can be an optional.

Stage-3 fixer run: those four overrides now have a test of their own, `SummonedObjectsTest.TheFourSubclassOverridesKeepJavasEmptyMasterName`.
It builds a real `SummonedHouseNpc` from a `House` without an owner (`SummonedHouseNpc.java:19-20`) and a `Homing`, `Servant` and `Trap` through
subclasses that replace only their `AION_UNPORTED` `setupStatContainers` with the closest base Java derives the missing stat container from
(`SummonedObjectGameStats` for homing and servant, `NpcGameStats` for the trap, `TrapGameStats.java:14`), and asserts for each that
`getMasterName()` is `""` while `SummonedObject::getMasterName()` would answer the creator's name. Before it, the file only set `""` on a
`TestSummonedObject` that has no override and re-stated in its own expectation what the overrides do, so rewriting any of the four to call the
base kept every test green.

## Wave 5a, stage 3 (code-findings lane, fixer run): a material template without skills

Filed here because this is the deviations file the stage-3 fixer owns and the finding was recorded nowhere. By subject it belongs with the other
`game-server / world` rows of [P4-10.md](P4-10.md); the P4-10 owner may move it there unchanged.

| Area | Java | C++ | Reason |
|---|---|---|---|
| `MaterialTemplate.getSkills()` (`MaterialTemplate.java:27-29`) for a `<material>` element without a `<skill>` child | Returns the raw JAXB list, which JAXB leaves **null** for a missing element, so the for-each of `MaterialZoneHandler.java:46` throws a `NullPointerException` | The generated `MaterialTemplate` holds a `std::vector<MaterialSkill>` (`generated/aion/gameserver/model/templates/materials/MaterialTemplate.h`) and returns it empty, so the loop of `MaterialZoneHandler.cpp:51` never runs a body, `matchingSkills` stays empty and `onEnterZone` returns at `:55-56` | The C++ answer is the sane one and is kept. Test: `MaterialZoneHandlerTest.AMaterialWithoutSkillsIsANoOpWhereJavaThrows` |

`game-server/data/static_data/mesh_materials/material_templates.xml:84-87` has exactly four such entries — `<material id="121" skill_obstacle="1"/>`
through `<material id="124" skill_obstacle="4"/>`, ids 121, 122, 123 and 124: of the file's 35 `<material>` elements these four are the only ones
without a `<skill>` child, and the only ones that carry `skill_obstacle` (the other 31 hold the 34 material skills between them).
They are not filtered out on the way to the handler: `ZoneService.createMaterialZoneTemplate` (`ZoneService.java:194-213`) returns early only for
`ZoneName.NONE`, for material 11 (the shield, `ShieldService.tryRegisterShield`) and for a material id `MATERIAL_DATA` does not know, and builds a
`MaterialZoneHandler` for everything else. So in Java the first creature that enters the zone of a mesh whose material id is 121-124 throws out of
`onEnterZone`, where nothing catches it — the failure mode that cost the real-client session of 2026-09-21 thirteen npc spawns
(m5a-client-session.md F-1: `VisibleObjectSpawner` only logs "Error during spawn"). Whether the 4.8 client geo data actually carries a mesh with
one of the four ids was **not** checked (the geo files are binary and the M5a gate runs without geodata, plan §5.1); the entries exist, so the
handler would be built for such a mesh.

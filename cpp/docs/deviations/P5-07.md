| Area | Java | C++ | Reason |
|---|---|---|---|
| `sendItemUpdatePacket` / `sendStorageUpdatePacket`, legion warehouse kinah of a player without a legion | `sendPacket(player, new SM_LEGION_EDIT(0x04, player.getLegion()))` queues the packet with a null legion and the caller goes on. On the write thread, `AionConnection.writeData` -> `AionServerPacket.write` has already put the 2-byte length, the 5-byte opcode header and the 0x04 byte into `con.writeBuffer` when `writeImpl` throws the NullPointerException (`legion.getLegionWarehouse()`). Nothing catches it before `Dispatcher.run`, which logs it at ERROR, and the rest of that dispatcher pass is skipped: the other selected keys wait for the next select, and `processPendingClose` does not run. The buffer is left at position 8 with limit = capacity and OP_WRITE still set, so the next `Dispatcher.write` sends the stale, unencrypted rest of the buffer (capacity - 8 bytes). This corrupts the client's stream and in practice ends the session | The packet is not built when `getLegion()` is null. The client receives nothing and its stream stays intact | A deliberate departure from a Java defect. C++ serializes in the caller (`AionConnection::sendPacket`), so building the packet would throw into the caller instead; the precedent is MotionList's SM_MOTION (P4-12.md). `sendStorageUpdatePacket` then still throws at `SM_CUBE_UPDATE.cubeSize(LEGION_WAREHOUSE, player)`, in the caller, as Java does |
| `sendItemDeletePacket` | `Objects.requireNonNull(storageType)` | No check | `StorageType` is a value in C++; the callers that hold an unknown storage id throw the NullPointerException before the call (`Storage.cpp` `requireStorageTypeById`) |
